# Cosmosimulator — правила идентификаторов и записей реестра (v1)

**Статус:** утверждённые правила именования; приведённые ниже ID являются **проектируемыми именами**, а не доказательством существования такой разметки в текущем HTML/JS.  
**Связанный документ:** [01-idea-v1.ru.md](01-idea-v1.ru.md).

## 1. Зачем два реестра в одной системе

Одна запись описывает **канонический компонент**, другая — **его применение в игровом модуле**.

- **Компоненты**: общие окна, заголовки, кнопки, меню, пункты меню, dropdown, treeview, tooltip, chart, Canvas entity marker; они имеют собственного владельца реализации CSS/JS и интерфейс поведения.
- **Элементы**: конкретная кнопка «Продать» локального рынка, меню корабля, заголовок окна рынка, точка промежуточного маршрута, дерево сектора, раскрывающийся узел дерева исследований.
- **Экземпляры**: конкретное железо, корабль, звезда, объект дерева, пункт маршрута, строка таблицы. Их ключи не превращаются в новые постоянные записи для каждого появления объекта.

Это позволяет одному CSS/JS-компоненту обслуживать много применений, **не сливая их игровые сценарии**.

## 2. Синтаксис ID

Каноническая форма ID: строчные латинские буквы, цифры и дефисы внутри сегментов, сегменты разделены точками.

- Тип компонента: `ui.<component>[.<variant>]`.
- UI-элемент: `<domain>.<feature>.<context>.<element>[.<part>]`.
- Для простого окна допустимы `market.window`, `market.window.title`, `market.window.close`.
- Форма динамического экземпляра: **`element_id` + отдельные структурированные поля контекста** (`resource_id`, `ship_id`, `station_id`, `route_stop_id`, `object_id` и т. п.).

Пример:

| Уровень | Значение |
|---|---|
| Общий тип | `ui.context-menu.compact` |
| Применение | `market.local.item.context-menu` |
| Конкретный объект | `element_id=market.local.item.context-menu`, `resource_id=iron` |
| Документированная краткая запись для человека | `market.local.item[iron].context-menu` |

Последняя форма — **человекочитаемое представление**, но канонический ID в реестре не содержит скобок с временными ключами.

### Ограничения

1. ID не зависит от видимого RU/EN текста, DOM-порядка, CSS-класса, пути файла, размеров окна или положения в меню.
2. ID нельзя повторно использовать для другой семантики. Устаревший ID сохранять как `deprecated` с ссылкой `replaced_by`.
3. В пределах общего реестра не может быть двух активных элементов с одним `element_id`.
4. Один и тот же шаблон в разных модулях получает разные `element_id`, но может ссылаться на общий `component_id`.
5. При перемещении элемента между DOM-контейнерами его ID сохраняется, если его семантика и роль для игрока не изменились.
6. Визуальный стиль, вариация плотности, состояние `disabled` и язык **не** создают новый ID; если реально различается поведение компонента — оформляется документированный `variant`.
7. Не включать в ID личные имена, токены, случайные GUID из рендера, переведённые строки, server session ID.
8. Смена публичного ID требует контролируемой миграции реестра и ссылок в тестах/документации, а не тихой замены.

## 3. Имена, сокращения и перевод

Каждая каноническая запись **обязательно** содержит:

- `name_ru` — полное название по-русски.
- `name_en` — полное название по-английски.
- `short_ru` — утверждённое русское сокращение.
- `short_en` — утверждённое английское сокращение.
- `kind` — тип: `window` / `button` / `menu` / `menu-item` / `tree` / `tree-node` / `map-object` / `chart` и т. д.
- `component_id` (для элемента) и `owner_module`.
- `description_ru` — конкретное назначение и границы применения.
- `implementation_refs` — проверенные пути/функции/селекторы/DOM-атрибуты после аудита.
- `status` — `proposed`, `verified`, `implemented` или `deprecated`.

Сокращения **не придумываются автоматически по первым буквам**: владелец утверждает читаемую форму. Они могут быть отличными от видимой подписи кнопки. Сокращение «ККМ» не должно означать одновременно «Компактное контекстное меню» и другое понятие. Если одинаковое сокращение потенциально нужно в нескольких модулях, добавляется контекст: `ЛР-ККМ` для локального рынка, `ПЛ-ККМ` для планеты, при сохранении общего `ККМ` у самого компонента. Для английского `CCM`, при необходимости `LM-CCM` / `PL-CCM`.

**Пример утверждаемой номенклатуры общего компонента:**

| Поле | Значение |
|---|---|
| ID | `ui.context-menu.compact` |
| Полное RU | Компактное контекстное меню |
| Полное EN | Compact context menu |
| Краткое RU | **ККМ** |
| Краткое EN | **CCM** |
| Назначение | Компактный список контекстных действий с проверяемыми состояниями и необязательным вложенным меню |
| Реализация | **Проверить по аудиту**, не объявлять отдельный компактный вариант уже существующим |

**Пример элемента модуля:**

| Поле | Значение |
|---|---|
| ID | `market.local.item.context-menu` |
| Полное RU | Компактное контекстное меню товара локального рынка |
| Полное EN | Local market item compact context menu |
| Краткое RU | **ЛР-ККМ** |
| Краткое EN | **LM-CCM** |
| Тип компонента | `ui.context-menu.compact` (**предварительное сопоставление**) |
| Владелец | `market` / локальная торговля |
| Контекст | `resource_id`, опционально `station_id` |
| Подменяет ли меню другого модуля | Нет, действия и права привязаны к локальному рынку |

При наведении на **ID-бейдж** элемента оба полных имени и обе краткие формы должны быть доступны, а также название **общего компонента**, если это полезно для диагностики.

## 4. Предварительный словарь типов компонентов

Это стартовая **номенклатура для согласования**, не фиктивная ведомость уже реализованных компонентов.

| Предлагаемый `component_id` | Полное RU / EN | Сокр. RU / EN | Предполагаемая база в коде |
|---|---|---|---|
| `ui.window.module` | Модульное окно / Module window | МО / MW | `ui/windows.js` |
| `ui.window.titlebar` | Заголовочная панель окна / Window title bar | ЗПО / WTB | `ui/windows.js` |

| `ui.context-menu.standard` | Контекстное меню / Context menu | КМ / CM | `ui/menu.js` |
| `ui.context-menu.compact` | Компактное контекстное меню / Compact context menu | **ККМ / CCM** | Нужен аудит; не утверждать наличие готового variant |
| `ui.dropdown.navigation` | Выпадающее навигационное меню / Navigation dropdown | ВНМ / NDM | `index.html` + CSS; сравнить с `ui/menu.js` |
| `ui.tooltip` | Всплывающая подсказка / Tooltip | ВП / TT | `ui/tooltip.js` |
| `ui.field.select` | Поле выбора / Select field | ПВ / SF | `ui/fields.js`, `ui/combobox.js` |
| `ui.tabs` | Переключатель вкладок / Tabs | ПВК / TABS | `ui/tabs.js` |
| `ui.tree.hierarchy` | Иерархическое дерево / Hierarchical tree | ИД / HT | `ui/disclosure.js` либо feature; проверять |

**Не навязывать новый `component_id` там, где текущий механизм уже имеет корректную стабильную идентичность.** Сначала инвентаризация текущего API.

## 6. Предлагаемая схема машинно-читаемого реестра

На этапе реализации создать один машинно-читаемый источник истины (например, JSON/TSV/CSV — формат выбирается после проверки существующих инструментов; предпочтителен простой JSON с валидацией). Читаемые MD-таблицы **генерировать из него**, а не поддерживать две расходящиеся базы.

Пример записи (формат **проектный**, не готовый API):

```json
{
  "id": "market.local.item.context-menu",
  "name_ru": "Компактное контекстное меню товара локального рынка",
  "name_en": "Local market item compact context menu",
  "short_ru": "ЛР-ККМ",
  "short_en": "LM-CCM",
  "kind": "menu",
  "component_id": "ui.context-menu.compact",
  "owner_module": "market.local",
  "parent_id": "market.local.panel",
  "context_keys": ["resource_id", "station_id"],
  "description_ru": "Меню действий над товаром в локальном рынке; не меню планетарного сектора.",
  "implementation_refs": [],
  "status": "proposed"
}
```

**Записи не должны заявлять `verified` до проверки актуального DOM/JS и поведения.**

## 7. Правила пополнения реестра

- Новые значимые UI-элементы регистрируются вместе с задачей на их создание.
- Разработчик ищет существующий `component_id` прежде, чем создавать ещё один стиль/JS-компонент.
- Если нужны новые визуальные различия — предпочтительны **варианты** общего компонента, а не копия всех CSS-правил под другим классом.
- Идентификаторы должны оставаться одинаковыми в RU и EN.
- Для всех записей обязательны полные имена и сокращения RU/EN.
- Применение DOM/Canvas/SVG должно позволять найти ID в живом интерфейсе в Debug UI.
- При удалении элемента оставлять документированный статус `deprecated` и, по возможности, `replaced_by`, а не использовать ID повторно.
- В тестах проверять уникальность ID и отсутствие ссылок на удалённые компоненты.

## 8. Отличие UI ID от CSS/HTML/API идентификаторов

`element_id` — язык постановки задач и семантики. Он **не** обязан буквально совпадать с HTML `id`, CSS-классом, строкой `data-open` или именем Go endpoint.

Соответствия фиксируются в `implementation_refs`. Переименования в коде допускаются только при необходимости реализации и с отдельным регрессионным тестом. **Не выполнять глобальную замену существующих ID без проверки поведения.**
