# Cosmosimulator — аудит, стандартизация и внедрение реестра UI (v1)

**Статус:** проектный план, без разрешения менять рабочий код прямо сейчас.  
**Цель:** сначала установить идентичность всех значимых элементов, затем убрать реальное дублирование UI-реализаций **без изменения игровых правил и поведения**.

## 1. Почему проблема реальна, но её нужно измерить

Текущий frontend уже разделён на `core`, `ui`, `features`, `styles`. Общие окна и меню есть в `internal/server/web/ui/`, а экран рынка, планетарная сцена и галактическая карта — отдельные features.

Предварительно подтверждено:

- `ui/windows.js` уже управляет окнами, заголовками и оконными действиями.
- `ui/menu.js` содержит общую реализацию `UI.menu`, которая строит пункты и вложенные подменю.
- `index.html` содержит отдельные `<details class="dropdown">` для меню администратора и профиля.
- `styles/terminal.css` содержит несколько блоков правил для `.context-menu`, `.module-window`, `.dropdown` и других селекторов.

**Повторы CSS-селекторов сами по себе не означают ошибки:** часть правил — слои каскада, плотность, состояния `hover`, адаптивные экраны, поправки раннего рефакторинга. Аудит должен показать **семантически совпадающие реализации**, а не просто найти повторяющиеся слова.

Старый `docs/refactoring/ui/components.md` — исторический реестр семейств C01–C36. Он не заменяет новую идентификацию **каждой конкретной кнопки, меню, дерева и элемента карты**, но служит хорошей опорой.

## 2. Этап UI-R0 — полный инвентаризационный аудит

Вход: актуальный `main`, действующий JS/HTML/CSS, каталог `docs/refactoring/ui/CATALOG.ru.md`, старый аудит `components.md` и живой браузерный UI.

Составить **две связанные ведомости**:

1. **Семантические элементы:** модуль/окно/путь/тип/имя RU/EN/сокращение RU/EN, назначение, ближайший родитель, состояния и интеракции.
2. **Реализации:** общие функции `ui/*`, локальные JS-компоненты, CSS-селекторы/токены, HTML-шаблоны, вложенные меню, DOM/SVG/Canvas.

Включить всё доступное: навигацию, окна, администрирование, рынок, корпоративные действия, автоматизацию, исследования, объекты/карты, планетарные сцены и динамические элементы, в том числе **промежуточные точки маршрута, узлы дерева и природные деревья**.

Особенно проверить:

- Где разные features вручную создают однотипные меню вместо существующего `UI.menu`?
- Есть ли два разных JS/HTML-«компактных контекстных меню» с одинаковым поведением?
- Где одинаковые CSS-правила скопированы под двумя классами, и можно ли заменить модификатором общего класса?
- Где похожие элементы на деле **должны оставаться разными** из-за клавиатурного управления, permission, жизненного цикла, режима touch или игрового контракта?
- Какие элементы Canvas/SVG требуют отдельного механизма hit-test?
- Где один внутренний DOM ID/селектор используется для разных семантических операций?

Отчёт должен иметь уровни достоверности: **verified from code**, **verified visually**, **inferred / needs review**. Не заявлять полный охват только на основе поиска `button` в файлах.

## 3. Этап UI-R1 — утверждение реестра имён

На основе [02-naming-convention.ru.md](02-naming-convention.ru.md):

- Согласовать имена RU/EN, сокращения RU/EN и канонические ID.
- Установить связи `element_id → component_id → owner_module → implementation_refs`.
- Описать разные варианты компонентов отдельно от независимых копий реализации.
- Оставить старые ID как алиасы/**deprecated** при миграции, не менять исторические ссылки молча.
- Подготовить машинно-читаемый источник истины и его человекочитаемый Markdown-экспорт.
- Ввести проверку `ID collision`, отсутствующих языков/сокращений, ссылок на несуществующий компонент и дублирования сокращений в общей области.

**Результат:** один реестр, на который могут ссылаться владелец игры и два разработчика.

## 4. Этап UI-R2 — внедрение идентификаторов в существующие компоненты

Изменять код только после отдельного утверждённого ТЗ.

- Привязать канонический ID к `Modules.create` и элементам окна (заголовок/закрытие/действия).
- Поддержать контекстные ID у `UI.menu`, его пунктов и вложенных подменю; общий JS остаётся один.
- Добавить стабильную разметку для кнопок, форм, табов, строк и списков.
- Для общих компонентов предусмотреть объявление `component_id`, для feature — `element_id`.
- Для Canvas/галактической карты/планетарной сцены разработать **узкие feature-owned адаптеры** взаимодействия; не импортировать игровую механику в `ui`.
- Реестр не должен требовать второго набора окон, CSS-фреймворка или сборщика.

Поддерживать совместимость с существующими `data-open`, сохранённой геометрией окон, локализациями, правами и игровой логикой.

## 5. Этап UI-R3 — административный Debug UI

Реализовать [03-debug-ui.ru.md](03-debug-ui.ru.md) с двумя подрежимами; безопасный выбор без исполнения действий, бейдж ID и карточка RU/EN + сокращения по наведению на ID.

Начать со shell, окон, меню, рынка и административных разделов. Затем подключить деревья/таблицы и Canvas/сцены. Отсутствующий ID явно показывать как диагностику, а не выдумывать из CSS.

Утвердить visual/a11y/permission тесты. Только реальная серверная роль даёт доступ к Debug UI; на обычных игроках не должно быть эффекта.

## 6. Этап UI-R4 — приведение интерфейса к единым стандартам

**Только после инвентаризации.** Для каждой обнаруженной пары похожих реализаций решать:

| Ситуация | Решение |
|---|---|
| Совпадают назначение, поведение, доступность и lifecycle | Переиспользовать **один компонент** и один набор канонических CSS-правил |
| Отличается только плотность/отступы/размер | Один компонент плюс документированный `variant`/modifier |
| Отличаются permission, действия, API, модель данных | Общая визуальная оболочка при необходимости, **разные feature adapters** |
| Отличаются keyboard/hover/touch или accessibility semantics | Не объединять поведение силой; общий только безопасный нижний уровень |
| Повтор CSS связан с media/state/cascade | Сохранять до подтверждения, что объединение не меняет UI |
| Два имени обозначают один компонент | Каноническое имя + deprecated alias, миграция употреблений |
| Одинаковый текст кнопки в разных модулях | Разные `element_id`, общий `component_id` при совпадении механизма |

Стандартизировать в первую очередь:
- Плотности, высоты и состояния кнопок/полей, базовые токены `styles/tokens.css`.
- Внешний вид и API окон/панелей/заголовков и действий.
- Контекстные меню и **компактное контекстное меню**: один смысл, одна спецификация варианта, не две конкурирующие CSS/JS-ветки.
- Dropdown vs context menu: различить назначение прежде, чем объединять.
- Клавиатура, контраст, hit area, позиционирование popup и фокус.
- Пустые состояния, ошибка, загрузка, подтверждение, поиск.
- Семантику интерактивных элементов деревьев, графов, маршрутов и карт.

**Не** менять серверные DTO, цену товаров, механику торговли, перемещение персонажа, права или данные миров ради визуальной унификации.

## 7. Этап UI-R5 — автоматические проверки и сопровождение

Добавить к текущим `tests/ui` и архитектурным тестам:

1. Уникальность активных `element_id` / `component_id`.
2. Полноту RU/EN полного имени и сокращений.
3. Валидность ссылок на владельцев/компоненты и отсутствие оставленных `deprecated` применений после согласованной миграции.
4. Наличие регистрационного ID у согласованных обязательных типов элементов в динамически сформированном DOM.
5. Проверки общих CSS-элементов и снапшотов до/после унификации.
6. Отсутствие случайного выполнения действий в режиме «Выбор элемента».
7. Отдельную проверку Canvas hit-test и контекстных ключей без утечки секретных данных.
8. RU/EN, narrow viewport, браузерный zoom, mouse, keyboard и touch (где поддерживается).
9. Предохранители прав администратора, logout и отсутствие влияния debug overlay на обычных пользователей.
10. Производительность Debug OFF и отсутствие накопления обработчиков после открытия/закрытия окон.

Добавление значимого элемента в дальнейшем — часть Definition of Done: создать/обновить запись и проверить новый ID.

## 8. Порядок безопасного внедрения

Рекомендуемая очередь:

| Волна | Область | Почему |
|---|---|---|
| A | Shell, общее окно, admin/profile dropdown, контекстные меню | Максимальное переиспользование, удобное включение Debug UI |
| B | Рынок, корабль/трюм, формы/таблицы/вкладки | Много похожих элементов с разной бизнес-семантикой |
| C | Корпорации, исследования, планировщик, администрации | Вложенные меню, деревья, сложные формы и права |
| D | Галактическая карта: звёзды, маршруты, промежуточные точки, ветви | Canvas и структура маршрутов требуют специализированного hit-test |
| E | Планетарный режим: сектора, объекты природы, персонажи, площадки | Canvas, пространственный контекст, скрытые данные и нагрузка |
| F | Будущие Chat / Economic UI | Новые модули должны следовать реестру с момента проектирования |

Волны не обязаны совпадать с номерами релизов. Каждая завершается регрессионными тестами; не смешивать полный CSS-рефакторинг с миграциями PostgreSQL или переработкой игровых алгоритмов.

## 9. Минимальное ТЗ исполнителю следующего этапа

> Изучи актуальный `main` Cosmosimulator и существующий каталог UI. Проведи полную инвентаризацию всех значимых DOM, SVG и Canvas элементов. Создай проверенный семантический реестр с уникальными ID, полными названиями RU/EN и сокращениями RU/EN. Разделяй тип общего компонента, конкретный элемент в модуле и его динамический экземпляр. Обнаружь дублирующиеся CSS/JS реализации, составь отчёт с доказательствами и предложи безопасную унификацию, но **не объединяй классы/функции автоматически**. Проектируй Debug UI в административной панели: при наведении показывать ID, при наведении на ID — имена и сокращения; режимы «Просмотр»/«Выбор» без выполнения игровых действий. Отдельно учти деревья, маршруты и Canvas карты. Перед любым изменением игрового кода представить владельцу план и критерии приёмки.

## 10. Условия завершения проекта унификации

Работу считать завершённой не после появления красивой подсказки, а когда:
- владелец игры может **однозначно назвать любой значимый элемент** и скопировать ID из игры;
- два разработчика используют одни и те же имена RU/EN и сокращения, а не догадки;
- однотипные компоненты имеют **единого ответственного за стиль и поведение**, при этом бизнес-контекст каждого feature не теряется;
- реестр и реальная UI-разметка проверяются автоматизированно;
- исходный игровой интерфейс, доступность и правила не регрессировали.
