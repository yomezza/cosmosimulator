# Cosmosimulator — реестр элементов интерфейса (первая версия идеи, v1)

**Дата:** 2026-10-31  
**Статус:** согласованная идея; проработка реализации и инвентаризация ещё предстоят.  
**Репозиторий:** `yomezza/cosmosimulator`  
**Раздел:** `docs/ideas/ui-element-registry/`  
**Назначение:** единая система названий элементов UI для владельца игры, frontend-разработчика, backend-разработчика, тестировщика и проектировщиков новых модулей.

## 1. Задача

У каждого **значимого элемента интерфейса** должен быть устойчивый идентификатор, полное название **на русском и английском**, а также согласованное сокращённое название. Владелец Cosmosimulator должен иметь возможность назвать конкретный элемент в задании, скопировав его ID из самой игры, без скриншота с неоднозначным «это меню справа».

Параллельно нужно привести **визуально и функционально одинаковые компоненты** к общим стандартам. Одинаковое контекстное меню в двух модулях не должно получать две самостоятельные реализации или два конкурирующих CSS-стиля только потому, что разные разработчики назвали его по-разному.

**Важно:** единые компоненты не означают единые игровые действия. Контекстное меню рынка и контекстное меню планеты остаются разными экземплярами/сценариями с разными правами и содержимым, даже когда используют один UI-компонент.

## 2. Три независимых уровня идентичности

| Уровень | Что обозначает | Иллюстрация |
|---|---|---|
| **Тип компонента** | Повторно используемый визуальный/поведенческий механизм | `ui.context-menu.compact` — «Компактное контекстное меню», **ККМ** / «Compact context menu», **CCM** |
| **Элемент в конкретном модуле** | Конкретное назначение и место UI | `market.local.item.context-menu` — меню товара локального рынка |
| **Экземпляр элемента** | Конкретная строка, товар, корабль, маршрутная точка или объект сцены | `market.local.item.context-menu` + контекст `resource_id=iron` |

В реестре фиксируется связь «элемент модуля → тип компонента → фактические файлы JS/CSS/HTML», но это **не** три конкурирующие реализации.

Если одно и то же меню построено через `UI.menu` в двух функциях, оба элемента имеют собственные ID модуля, но один `component_id`. Если обнаружено два альтернативных CSS/JS-компонента с одинаковым назначением — это предмет аудита и возможной консолидации, а не повод оставить дубль ради совпадения с ID.

## 3. Границы реестра

Включить **все значимые элементы**, не только кнопки:

- Shell, навигацию, административные меню, заголовки, панели, окна и управление окнами.
- Кнопки, поля, переключатели, выпадающие списки и их пункты, вкладки, формы и подсказки.
- Контекстные меню, **каждый вид меню и его пункты**, в том числе вложенные и компактные варианты.
- Таблицы, колонки, строки/ячейки при необходимости, карточки, графики, индикаторы, статусные области, уведомления и диалоги.
- Деревья навигации, иерархические списки, вложенные узлы, ветви, раскрытие/сворачивание.
- Галактическую карту, звёзды, маршруты, **промежуточные точки, узлы и ветвления маршрутов** — даже если они рисуются Canvas.
- Планетарную карту, сектора, деревья и прочие природные объекты, маркеры, площадки и персонажей: интерактивные сущности сцены учитываются **по типу и семантике**, а не как каждый физический пиксель.
- Компоненты будущих модулей: Chat Service и Economic Service с собственными пространствами ID.

Обычные декоративные линии, внутренние обёртки DOM без самостоятельного назначения и отдельные пиксели Canvas регистрировать поштучно не нужно. При необходимости допустим ID составного блока плюс отдельные ID его значимых частей.

## 4. Административный режим «Отладка интерфейса» / Debug UI

**Обязательное требование.** В панели администратора предусмотреть пункт/раздел «Отладка интерфейса», где администратор включает и выключает **Debug UI**.

- **Выключено:** обычный игровой интерфейс, нет отладочных рамок, идентификаторов, перехвата ввода или иных видимых эффектов.
- **Включено:** при наведении/фокусировании значимого элемента показывать подсветку и **обязательно видимый ID** элемента.
- **Наведение на сам отображённый ID:** расширенная карточка с полным названием **RU / EN**, сокращением **RU / EN**, типом компонента, родительским модулем и возможностью **копировать ID**.
- Для типа «Компактное контекстное меню» карточка должна показывать, в частности, **«Компактное контекстное меню» / «Compact context menu»**, **«ККМ» / «CCM»**, а для конкретного меню — его отдельное название и ID.
- Два подрежима: **«Просмотр»** (обычные действия работают) и **«Выбор элемента»** (клик фиксирует ID, не запускает действие).
- Режим доступен только действующему администратору и применяется только к его интерфейсу, не ко всем игрокам. Настройка может восстанавливаться персонально при следующем входе администратором, но после выхода/потери прав режим прекращается.
- Для элементов Canvas/SVG требуется семантический hit-test или другая адаптация, а не фиктивный DOM-узел на каждый рисуемый объект.
- Показ ID и копирование не должны раскрывать секреты, сессионные токены, скрытую игровую геологию и данные, которые администратору не предназначено показывать данным UI.

Реализацию и критерии безопасности описывает [03-debug-ui.ru.md](03-debug-ui.ru.md).

## 5. Утверждённые решения Р-1…Р-8

1. **Р-1 — полный охват** значимых элементов, включая разные деревья, графы, элементы галактической карты и интерактивные объекты.
2. **Р-2 — раскрытие сведений:** ID виден при наведении на элемент; при наведении на ID — полное русское и английское имя, сокращения, тип, родитель; копирование.
3. **Р-3 — два подрежима:** «Просмотр» и безопасный «Выбор элемента».
4. **Р-4 — включение администратором** в панели администратора, локально для его сеанса/браузера; возможно персональное восстановление состояния.
5. **Р-5 — тип и экземпляр:** различать элемент реестра и отдельный объект/товар/строку/узел.
6. **Р-6 — без насильственного переименования существующего кода:** ID реестра — стабильный публичный контракт команды; связывается с текущими DOM ID, функциями, CSS и файлами.
7. **Р-7 — «единый интерфейс» значит единые стандарты и компоненты**, по итогам аудита, **а не** объединение бизнес-функциональности разных игровых модулей.
8. **Р-8 — постоянное сопровождение:** каждый новый значимый элемент должен получать запись в реестре; нужны автоматические проверки полноты и уникальности там, где это технически возможно.

Сейчас это **согласованная продуктовая идея**, а не заявление, будто UI уже размечен идентификаторами.

## 6. Учёт текущего проекта

В действующем frontend уже есть единые механизмы окон, меню, подсказок, вкладок и другие общие примитивы. Поэтому **перед реализацией** читать:

- [Каталог текущего интерфейса](../../refactoring/ui/CATALOG.ru.md).
- [Правила frontend-разработки](../../refactoring/ui/DEVELOPMENT.ru.md).
- [Исторический аудит компонентов](../../refactoring/ui/components.md); ссылки на старые JS-пути в нём исторические.
- `internal/server/web/ui/windows.js`, `ui/menu.js`, `ui/floating.js`, `ui/tooltip.js`.
- `internal/server/web/features/shell/navigation.js`, `features/maps/galaxy.js`.
- `internal/server/web/styles/tokens.css`, `styles/terminal.css`, `index.html`.

Проверенный предварительный факт: `ui/menu.js` содержит единый `UI.menu` с поддержкой вложенных меню; `index.html` также содержит штатные dropdown-меню административной панели и профиля. В `terminal.css` есть несколько групп правил для `.context-menu` и `.module-window`. **Это признаки необходимости аудита, но не доказательство лишнего CSS:** возможны каскад, состояния, responsive и сознательное разделение поведения.

Нельзя из-за этой идеи переписывать текущий UI-framework, вводить независимый frontend build-tool или второй механизм окон/всплывающих элементов.

## 7. Результат будущей проработки

Требуется:

1. Согласованная спецификация именования и схема записей — [02-naming-convention.ru.md](02-naming-convention.ru.md).
2. Дизайн безопасного Debug UI — [03-debug-ui.ru.md](03-debug-ui.ru.md).
3. Пошаговый аудит и план унификации — [04-unification-roadmap.ru.md](04-unification-roadmap.ru.md).
4. **Фактический машинно-читаемый реестр на следующем этапе**: собрать реальные элементы из актуального исходного кода и живого UI, определить стабильные ID, сопоставить владельцев и реализации, отделить проверенные факты от предлагаемых имён.
5. Отдельное ТЗ разработчику с тестами, этапами миграции и правилами сопровождения.

Документы в этой папке **не являются разрешением** прямо сейчас рефакторить HTML/JS/CSS или вводить новое административное API.
