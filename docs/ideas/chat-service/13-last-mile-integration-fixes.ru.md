# Chat Service — дополнительные критичные интеграционные уточнения v1.2

**Приоритет:** 01+02 (правила владельца) → 13 (исправления нижеперечисленных конкретных интеграционных проблем) → 08–12 (основной актуальный проект) → 03–07 (первоначальный проект). Для прочих положений 08–12 сохраняют приоритет. Если эти изменения не реализованы, нельзя отмечать соответствующие проверки пройденными.

## P0-01. SELECT ... FOR SHARE не совместим с обещанным только SELECT к чужим таблицам

В 03/06/09/10 одновременно заявлены два требования: Chat не имеет UPDATE к Planet-owned visit и Cosmic-owned company, однако в короткой Chat-транзакции использует SELECT ... FOR SHARE. В PostgreSQL для SELECT ... FOR SHARE, равно как FOR UPDATE, **нужно право UPDATE минимум на один столбец**, даже если SQL ничего не модифицирует. Таким образом, на заявленных GRANT запись/компиляция операции закончится ошибкой прав. Документация: https://www.postgresql.org/docs/current/ddl-priv.html (раздел UPDATE).

**Окончательный выбор реализации:**

- Не выдавать chat_runtime прямой UPDATE на users, companies, company_roles или Planet-owned visit. Не обходить ошибку прав выдачей владельца/superuser.
- Создать **узкие SECURITY DEFINER** функции (новые объекты обязательно chat_): chat_lock_company_access(actor_id, company_id) и chat_lock_planet_presence(actor_id). Владелец функции — отдельная ограниченная миграционная/сервисная DB-роль, обладающая минимально необходимым SELECT и UPDATE-привилегиями к точно названным fence-строкам. Chat runtime имеет только EXECUTE и не может менять чужие данные самостоятельно.
- Обе функции LANGUAGE plpgsql, VOLATILE, SECURITY DEFINER, со строго фиксированным безопасным search_path (целевой quoted DB_SCHEMA + pg_catalog; не public и не каталог объектов вызывающего), явными schema-qualified ссылками и без dynamic SQL. Отозвать PUBLIC EXECUTE, затем GRANT EXECUTE только chat_runtime; отсутствие общего CREATE в указанной схеме для недоверенных ролей проверить тестом. Возвращаемые данные — только необходимые поля разрешения, без password_hash, cookie или контента других визитов.
- Вызов — **в уже открытой короткой транзакции Chat**, до изменений сообщения. Lock живёт до COMMIT/ROLLBACK; нельзя выполнять вызов autocommit, а затем посылать сообщение в другой транзакции.
- Для Planet функция SELECT authoritative visit FOR SHARE, валидирует active/current surface+sector/visit epoch/freshness; авторитетный writer Planet делает UPDATE **этой же строки** при смене сектора/leave/revoke. **До появления real P2-4+ fields функция не должна быть включена; spatial remains disabled.**
- Для company есть дополнительная гонка, требующая самостоятельного fence P0-02. Функция company lock должна захватывать только этот fence, затем обычным SELECT получать company/member/roles в той же транзакции; **не** захватывать users FOR UPDATE и не заводить блокировки в обратном порядке.
- Проверить каждый GRANT реальным тестом, переключившись на runtime DB role. SELECT и EXECUTE должны работать, UPDATE чужой пользовательской/планетарной строки — 42501; запрос с заведомо чужим actor/visit не даёт данных. User_id функции всегда берётся из серверно проверенной сессии, а не JSON от клиента.

Это **не** перенос игровой авторизации в PostgreSQL. SQL-функция удерживает fence и отдаёт авторитетный снимок; Go AccessResolver всё равно определяет полномочия и политику.

## P0-02. Уже существующий порядок блокировок корпораций несовместим с наивным corporate send

Проверено по текущим файлам:
- internal/corporations/directory.go, CompanyAction: BEGIN → SELECT users.company_id FOR UPDATE → при leave затем SELECT companies.owner_id FOR UPDATE (путь **user → company**).
- internal/corporations/commands.go, CorporationCommand: CompanyAccess читает пользователя, затем блокирует SELECT companies.id FOR UPDATE, после чего role_assign может UPDATE users.company_role, company_dissolve массово UPDATE users и DELETE companies (путь **company → user**).
- В 08/10 предложено во время отправки в Corporation блокировать company FOR SHARE и проверить membership, но без единого порядка блокировок это может стать третьим конфликтующим путём. Простое read users без fence допускает отправку по членству, изменённому между проверкой и COMMIT.

**Выбранный узкий механизм сериализации, не требующий от Chat блокировать обе Cosmic-owned таблицы:**

1. Новая **chat_company_access_fences**: company_id BIGINT PRIMARY KEY, revision BIGINT NOT NULL DEFAULT 1 CHECK(revision>0), updated_at TIMESTAMPTZ; **единственный писатель — Cosmic**. Новые записи Cosmic создаёт в транзакции создания компании; для действующих компаний migration backfill INSERT ... SELECT с ON CONFLICT DO NOTHING.
2. **Каждый** Cosmic-обработчик, меняющий членство пользователей, назначенные роли, JSONB permissions, владельца корпорации или переход компании в deleting, в **той же транзакции** выполняет UPDATE chat_company_access_fences SET revision=revision+1, updated_at=clock_timestamp() для **каждой затронутой компании**. Сначала собственные Cosmic updates, затем fence updates. При переходе пользователя C1→C2 меняются fences обеих компаний в порядке company_id ASC. Если в Cosmic есть новые/скрытые mutators, их выявить SQL search и покрыть тестами — список выше не исчерпывает все будущие пути.
3. Chat corporate READ/SEND/SEARCH/MODERATION: в одной SQL tx функция chat_lock_company_access блокирует **только fence row FOR SHARE** (с привилегией владельца функции), затем обычным SELECT читает users.company_id, company_roles.permissions, companies.owner_id и companies.chat_deleting. Нельзя доверять ранее считанному membership из handshake или делать lock users/companies FOR SHARE поверх fence.
4. Корректность: если Cosmic транзакция изменила users/companies, но ещё не захватила fence, Chat под fence видит только **старое committed состояние**; Cosmic не сможет закоммитить изменение, пока Chat не освободит fence. Если Cosmic уже завершила COMMIT, Chat читает новое состояние. Так send и отзыв прав имеют определённый порядок без нового Chat-owned UPDATE users/companies.
5. Cosmic в собственной транзакции должен совершать **полное обновление требуемых fences до COMMIT**. Если из-за отсутствующего fence или SQL ошибки update не прошёл, откатить **всё** изменение членства/ролей: нельзя завершить JOIN/LEAVE без инвалидации доступа.
6. chat_runtime имеет к chat_company_access_fences только EXECUTE через функцию и не имеет UPDATE; Cosmic пишет fence. Функция возвращает ошибку/отказ при отсутствующем fence, deleting либо несовпадении company. Нет fail-open при ошибке.
7. Текущие Cosmic workflows user→company и company→user **по-прежнему могут конфликтовать между собой**. До релиза нормализовать существующие порядок и/или применить bounded SQLSTATE 40P01/40001 retries по операциям Cosmic — не маскировать проблему Chat lock-ом. Chat не добавляет к ним новое user/company row-lock inversion.

**Дополнительный DDL:** chat_company_access_fences в PostgreSQL-каталоге 09 (добавление v1.2), chat_lock_company_access и chat_lock_planet_presence — две новые функции. Не создавать отдельные копии таблиц companies/users.

**Тесты нового режима:**
- GATE01: 100 параллельных sends + Cosmic leave той же учётной записи: ни одного сообщения в старой Corporation после COMMIT leave; никакой deadlock.
- GATE02: одновременное role_assign и чужой corporate mute/send: последний при новом запрете видит актуальную роль; нет успешной операции после COMMIT отзыва.
- GATE03: company_dissolve начинает deleting, Chat send конкурирует: все sends упорядочены до либо после transition, после COMMIT deleting нет новых; чат очищается, refund ровно один.
- GATE04: миграция backfill, создание новой company, leave/join, role_save, role_delete, role_assign, company_transfer, request_accept/согласие на вступление, company_dissolve и возможные admin commands: каждая изменяющая операция выполняет fence update в одной TX; отсутствие fence блокирует commit.
- GATE05: chat_runtime без UPDATE на users/companies/planet_visits и fence, но с EXECUTE на chat_lock_*; direct SELECT ... FOR SHARE чужой таблицы без UPDATE отклонён; сообщения/чтение разрешены через функции только при правильном access.

## P1-03. Поиск по русскому тексту зависит от collation базы

- Требование продукта: регистронезависимый поиск по русскому и английскому, подстроки и точные emoji.
- lower() в PostgreSQL зависит от collation/locale, а collation C/POSIX не обеспечивает обычные языковые правила для не-ASCII. Нельзя считать, что lower('ПрИвЕт') обязательно корректен в любом развёртывании. Документация: https://www.postgresql.org/docs/current/collation.html.
- До миграции индексов проверить server_encoding, lc_ctype, доступность ICU и поведение конкретной collation на реальной целевой PostgreSQL. Договориться об **одной проверенной deterministic collation** для выражения lower(body COLLATE target) и точно такого же выражения в query + GIN gin_trgm_ops. Предпочтительно ICU при доступности; не полагаться на молчаливое переключение системной локали.
- Не создавать продублированный полнотекстовый search_body с сообщениями: требование об отсутствии скрытых копий текста. Если collation не может обеспечить тесты RU/EN, блокировать включение поиска и явно сообщить о недостающей предпосылке; не маркировать поиск готовым.
- Поиск **буквальной подстроки**: экранировать в запросе специальное значение %, _ и escape-символа для LIKE; иначе пользовательский ввод с % или _ интерпретируется как wildcard. Использовать bound parameters, а не конкатенацию SQL с текстом пользователя.
- Trigram index может не ускорять 1–2-символьные запросы, пунктуацию и отдельные emoji. Для такого ввода использовать ограниченные по доступному channel/time range bounded scans с LIMIT/statement_timeout либо иной измеренный план; никакого глобального непроверенного full scan.
- Проверить в реальной БД: ПрИвЕт/привет, МИР/мир, Ёж/ёж, Hello/HELLO, q='%'/'_'/'\\', emoji включая ZWJ, поиск «100%», отсутствие совпадений с недоступными scope, EXPLAIN на >100k строк. Не путать визуальный emoji glyph с одной Unicode codepoint.

## P1-04. Загрузка и восстановление связей с игровыми объектами

Игровые ссылки в 01 есть как продуктовая возможность, но 03–12 ещё не фиксируют **нормализованный allowlist конкретных целей**, поэтому Codex иначе придумает собственные ссылки.

Техническое решение v1: поддерживать только уже существующие в Cosmosimulator стабильные идентификаторы объектов, проверяемые сервером: company_id (companies.id), ship_id (ships.id с проверкой права на конкретный корабль), surface_id (planet_surfaces.id), sector=(surface_id,number) через planet_sectors, star ID из действующей модели галактики, если возможно устойчиво идентифицировать. Включать каждую категорию поэтапно только когда подтверждён стабильный ID, видимость и существующий route/game UI для перехода. Не вводить внешние произвольные URL как «игровую ссылку».

Формат WS entity — структурированная пара {kind,id} либо {kind,surface_id,sector_number}, **отдельно от body**. Сервер формирует безопасную display label; никогда не использовать клиентский HTML/href. Открытие ссылки требует текущих прав владельца игры даже если текст сообщения доступен. Объект удалён или стал закрытым → «Объект недоступен», исходное сообщение остаётся.

В 01/02 не утверждён конкретный перечень видов объектов. Если реализация нового вида ссылки требует изменения разрешённого игрового доступа, это **не техническое решение**, а отдельное согласование; Codex не должен угадывать.

## P1-05. Утечки текста и восстановление после резервной копии

- Свободная обязательная причина наказания может содержать вставленную цитату оригинала. Продукт требует обязательную причину, но техническая установка «в audit никогда не хранить body» означает: запрещать сохранение полного исходного текста в reason/metadata, нормализовать ограниченный reason code + короткий комментарий, не снапшотить сообщение. Исключить копирование body автоматически. Причина обязательна — допускается осмысленная краткая причина без цитирования.
- Нельзя восстановить PostgreSQL backup, созданный **до удаления**, и без иных источников доказать, какие moderator-deletions были после него: вместе с БД потеряны и «удалённые» записи об этом факте. Для гарантий после аварии либо PITR/WAL до актуальной committed точки со всеми deletion events, либо отдельный независимый защищённый erasure journal; иначе **fail-closed**: до ручной сверки/решения администратора Chat readiness не должен стать 200. Обычный TTL cleanup старых сообщений при restore обязателен, но **недостаточен** для модерационного удаления ещё не просроченных копий.
- Не создавать новый отдельный database product ради журнала; операционный путь с WAL/PITR предпочтителен. Политику резервирования и восстановления проверить в реальном эксплуатационном окружении, сейчас её нельзя доказать документами.

## P2-06. Защита от ресурсного спама без изменения игровых правил

Создание pending group без приглашений, массовые запросы history/search и бесконечный fanout @all способны расходовать ресурсы без нарушения лимита отправки сообщений.

- Нужны общие network-level bounded limits (concurrent requests, global WS frames/sec, JSON depth, WS queue, search query time, max pending maintenance) и сервисный мониторинг; это инфраструктурная защита, её default корректировать по нагрузке.
- При наполнении очереди уведомлений: durable DB state не терять, активную WS slow consumer отключать; при восстановлении клиент синхронизируется через bootstrap.
- Не вводить молча новые **игровые** лимиты вроде «не более N созданных групп в сутки» или «нельзя приглашать в новую группу ещё X часов»: они затрагивают правила игроков и требуют одобрения владельца. Для abuse prevention использовать прежде всего общий HTTP/WS rate/size/burst caps, TTL пустых pending groups из 10 и monitoring.
