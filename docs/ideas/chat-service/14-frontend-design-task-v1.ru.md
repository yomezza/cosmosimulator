## 1. Утверждённые требования владельца к внешнему виду

### Два режима **одного** Chat-модуля

**A. Плавающий (floating):**
- Самостоятельное **небольшое прямоугольное окно с прямыми углами**. Не квадратное по соотношению сторон: прямоугольное, **border-radius: 0** на внешнем контуре.
- Можно свободно перемещать, изменять ширину и высоту, закрывать/открывать; поведение согласовано с остальными модульными окнами игры.
- Плотная компоновка: **без толстых кнопок, огромных отступов, пустых декоративных областей**. Инструменты доступны, но не занимают половину высоты.
- Пользователь **настраивает прозрачность фона окна**. Содержимое (текст, иконки, поля ввода, меню) должно оставаться читаемым.
- В минимальных размерах окно остаётся функциональным: область переписки и отправка не исчезают.

**B. Закреплённый на главной странице (home-docked):**
- Тот же чат встроен непосредственно в главную игровую страницу **ниже панели** с информацией об аккаунте, кредитах, местоположении активного корабля и хронологии.
- Ширина **половина доступной основной области контента** (после учёта боковой панели). Вторую половину **зарезервировать под будущие новости**. **Не разрабатывать новости** в этом задании и не имитировать игровые новости.
- Закреплённый чат тоже остаётся **компактным**, но становится шире относительно обычного плавающего окна; использовать дополнительную ширину разумно, а не раздувать кнопки.
- Чат в закреплённом режиме — **часть потока страницы**, не `position: fixed` поверх игрового интерфейса.
- На узком экране разрешён адаптивный переход к одной колонке с чатом во всю доступную ширину; не пытаться удерживать два непригодных для чтения столбца по 50% на телефоне.

**Переход A ↔ B:** явные действия «Закрепить на главной» и «Открепить / Плавающее окно». Переход сохраняет выбранную вкладку, открытую беседу, текст черновика, положение прокрутки (или якорь видимого сообщения), настройки и состояние единственного Chat-транспорта. Ни второй WS-сессии, ни второго монтирования одного и того же контроллера.

**Форма и стиль:** терминальная эстетика Cosmosimulator — темный фон, привычная светлая типографика, акцент из имеющихся токенов, тонкие разделители; сам чат и его панели визуально **прямоугольные с прямыми углами**. Не менять ради этого скругление остальных модулей игры.

### Предварительные размеры **для прототипирования**, не новые игровые правила

- Floating desktop: стартовые примерно **420 × 540 px**, допустимо настраивать в пределах viewport. Ориентир: минимально пригодная ширина около **350–360 px**, высота около **360–400 px**. Фактические границы назначить после визуальных тестов; не сжимать до неработающего компонента.
- Floating: заголовок/панель действий ориентировочно 30–36 px, вкладки 30–34 px, ввод 40–56 px с автоподстройкой, плотная лента с нормальной высотой строк.
- Docked desktop: `grid-template-columns: minmax(0, 1fr) minmax(0, 1fr)`, gap около 12–16 px внутри блока ниже overview. Высота чата ориентировочно 480–620 px с **собственной прокруткой сообщений**, а не ростом всей главной страницы из-за 1000 сообщений.
- Прозрачность: предложить настройку **непрозрачности фона**, например 40–100% с шагом 5% и 100% по умолчанию. Это UX-ориентир: проектировщик должен проверить читаемость и при необходимости скорректировать нижнюю границу. Не делать CSS `opacity` на всем родителе, которая делает прозрачными текст и кнопки.

**Важные нюансы кода, требующие учёта в дизайне:**
- `ui/windows.js` автоматически прячет содержимое окна при `too-small` (<350 px по ширине или <220 px по высоте). Поэтому Chat нельзя просто уменьшить, не проверив этот режим: для минимального floating должен оставаться полезный layout. Рекомендуется корректный минимальный размер/локальный адаптивный вариант.
- `Modules.clearPrivate()` очищает **контент обычных окон**, `Modules.closeAll()` вызывается при logout. Если chat-root переносится из floating DOM в home slot, он **не будет автоматически очищен** этим механизмом. Нужен самостоятельный lifecycle cleanup на `signedout` / смену аккаунта.
- `ui/windows.js` хранит обычное `pinned` в `module:<id>`. **Отдельно** хранить `chat-dock-mode`: без этого старое свойство `pinned` ошибочно станет означать «докнут на главную».
- `.overview-stats` уже имеет responsive 4→2→1 колонки в CSS; размещаемый chat/news grid должен быть **самостоятельным**, ниже статистики, не менять её колонки и не съедать место у кредитов/местоположения.

## 3. Предлагаемая DOM-композиция (проект для последующего разработчика)

**Одна модель состояния и один ChatView**, размещаемый попеременно в двух оболочках:
1. `ChatFloatingHost` — обычное окно, созданное через `Modules.create("chat", ...)`, с локальным chat-specific header и стилями.
2. `ChatHomeHost` — встраиваемая часть `#game` под `.overview-stats`.
3. `ChatController` — независимо от расположения хранит вкладку, target conversation, scroll anchor, draft per conversation, loading states. Он **не перезапускается** при переключении контейнера. Ни второго fetch cycle, ни второго WS.

Ориентир новой минимальной домашней разметки (не требование буквально воспроизвести код):

```html
<div class="home-lower-grid">
  <section id="chat-home-slot" aria-label="Чат"></section>
  <section id="news-home-slot" aria-label="Место для будущих новостей"></section>
</div>
```

Если чат не закреплен, домашний grid может быть скрыт/свёрнут без фиктивного пустого вертикального блока; место для будущих новостей не должно заставлять игру показывать пустой модуль постоянно. Если закреплен, chat slot получает 50% доступной ширины. Пустая новостная половина резервируется на уровне компоновки; функциональность новостей не делать.

**Важно:** перемещать **chat-root** между host-ами, а не клонировать его и не создавать второй DOM/chat-view. Смена режима не должна уничтожать draft/selection/scroll; при необходимости хранить явный scroll anchor, а не абсолютные pixels.

**Floating:** связь с `Modules` в пределах публичного API. Если нужно добавить универсальный dock hook — очень маленький backward-compatible API с тестами, без изменения поведения других окон. Если проще реализовать специальный chat host-контроллер, он всё равно должен **использовать Modules** для floating, а не писать новый drag/resize с нуля. Существующая pin-кнопка в chat titlebar не должна вводить в заблуждение: проектировщик обязан отдельно решить её доступность/название или заменить **только для чата** действием «На главную».

**Dock:** чат не считается плавающим окном в `window-switcher`; пункт «Чат» в боковой панели при нажатии фокусирует/прокручивает страницу до закреплённого чата, а не создаёт дубликат floating. При откреплении снова открывается/фокусируется floating host; геометрия последнего floating сохраняется. Никаких двух видимых chat-root.

## 4. Состав компактного интерфейса

Делать **одну систему компонентов**, а не шесть разрозненных экранов. Порядок разделов **строго**: **Избранное → Global → Planet → Sector → Corporation → Private**.

### Компактная вертикальная структура

1. **Узкая шапка**: «Чат» или название открытой Private-беседы, индикатор состояния соединения, компактные действия (поиск, настройки/прозрачность, закрепить/открепить, закрыть в floating). Не занимать много строк.
2. **Лента из 6 разделов**: короткие кнопки/подписи или аккуратная горизонтальная прокрутка на малой ширине. Порядок постоянный. Недоступные по правам Planet/Sector/Corporation **скрыты или недоступны согласно 01–02**; при скрытии не отдавать доступ к их истории. «Избранное» первым всегда.
3. **Основная область**: либо сообщения текущего канала, либо список Private-бесед/приглашений, либо папки/записи Избранного, либо результаты поиска. Главное место отдано контенту, а не декоративным карточкам.
4. **Закреплённый снизу compose**: поле ввода, компактная кнопка отправки, optional reply preview и счётчик символов только когда полезно. Поле ввода не перекрывает историю. Disabled/нет доступа — понятная причина, без ложного активного поля.

При floating narrow Private: сначала список бесед, при выборе — заголовок с «Назад» + текущий разговор. Не держать постоянный sidebar шириной 200px в окне 350–420px. В docked, **если реально хватает места**, разрешено двухколоночное представление Private (список + история); общая панель сообщения/compose одна и та же. Для Избранного аналогично: папки можно скрывать за узким selector вместо постоянного бокового столбца.

### Сообщение

- Не делать толстые чат-пузыри в стиле мессенджера, если они расходуют место. Использовать компактные строки/сгруппированные сообщения в стилистике терминала.
- Автор, текущий тег его корпорации, локально отформатированное время, содержимое/эмодзи, при необходимости ссылочный preview или reply marker.
- **Planet:** перед каждым сообщением **номер исходного сектора**; название сектора в подсказке по hover/focus/tap. Заголовок содержит название текущей планеты.
- **Private:** рядом с отправленным сообщением серая точка до прочтения, синяя после прочтения **хотя бы одним другим участником**.
- **Троеточие** появляется при наведении/фокусе строки; по нажатию вызывает существующий `UI.menu` с «Сохранить в избранное» и «Пожаловаться»; дополнительные «Ответить»/«Удалить» — только при наличии прав. На touch контекстное действие доступно без hover.
- Не показывать по умолчанию большой набор постоянно видимых кнопок у **каждого** сообщения.
- Удалённый/просроченный оригинал ответа показывать как «Исходное сообщение недоступно», сам ответ остается.
- Текст — безопасный, не выполнять HTML из сообщений и не подставлять небезопасные URL.

### Состояния отдельных разделов

- **Global** — единая глобальная лента, индикация новых без числового счётчика, 256 символов, лимит отправки 1/3s.
- **Planet** — только при текущем active visit, 256, 1/2s; **Sector** — только в текущем секторе, 256, 1/1s; при смене сектора переписка переключается автоматически без доступа к прошлому сектору.
- **Corporation** — только текущая корпорация, 256, 1/1s; mute запрещает отправку, но **не** чтение/поиск; owner/модератору показать компактное действие модерации по правам, но не перегружать обычный интерфейс.
- **Private** — список бесед и приглашений, личные/группы, создание, принятие/отказ, название, владелец, участники, редактирование состава только владельцем, выход/передача/удаление с подтверждением; групповая переписка и read status. До первого принятия приглашения в новую группу писать нельзя; при DM→group приглашённый после accept получает доступ к старой истории. Лимит 500 и 10 сообщений/10s.
- **Избранное** — виртуальная «Все», папки, заметки и копии с источником/временем, поиск/перемещение; редактировать только личные заметки, не копии. Удаление папки не удаляет записи.
- **Поиск** есть в каждом из 6 разделов; по умолчанию компактная иконка раскрывает поисковую строку, вместо постоянно занимающего высоту блока.
- **Упоминания:** `@имя` с UI-подсказкой адресата по правам; `@all` работает только в Corporation и Private (включая личный DM). UI не выдумывает разрешение: окончательная проверка серверная.

## 5. Прозрачность окна

Проектировщик должен показать/описать конкретное UI-управление: компактная настройка **«Непрозрачность фона: N%»** внутри меню параметров Chat (при необходимости дополнительно в общих Настройках). Пользователь меняет в реальном времени, результат сохраняется для **своей учётной записи**.

**Не использовать** глобальное CSS `opacity` на `#window-chat`: тогда становятся прозрачными текст, кнопки, контекстные меню, tooltip, badges. Вместо этого применять изолированный полупрозрачный **фон оболочки/шапки/списка** через alpha-channel CSS переменную, сохраняя opacity текста и полей ввода 1. Предусмотреть достаточную контрастность на фоне карты/космоса; при необходимости отдельную более плотную подложку под ленту и compose. Прозрачность не должна давать ощущение пропадающих controls при наложении на яркую игровую сцену.

**Приоритет:** читаемость и возможность писать выше экстремальной прозрачности. Обе компоновки можно настраивать одной опцией; исходный вид — 100% для нормального первого запуска.

## 6. Взаимодействие с существующим состоянием UI и backend-контрактом

- Использовать server data как view model; сами верстка/компоненты должны работать на **демонстрационных mock DTO**, если Chat API ещё отсутствует. Никакой фейковой отправки в реальную игру.
- Не вводить дополнительную авторизацию Chat в браузере. Session и access контролирует backend (контракты 06/09/10/12/13). **Один активный Chat WS на аккаунт**, не создавать второй при dock/undock, открытии разных вкладок чата или смене космос↔планета.
- Cosmic down → блокировать все разделы; Planet down → только Planet/Sector; Chat down → показывать status «Нет соединения». Напечатанный, но не отправленный текст не отправляется сам после reconnect.
- Скрыть приватные данные и очищать runtime/drafts на `signedout`, `sessionexpired` и при смене account id. Важно, что часть геометрии может храниться локально, а UI preferences на backend описаны отдельно в `chat_user_settings`; проект должен чётко назвать **единственный источник истины** для каждой настройки, fallback и как избегать конфликтующих записей.
- `@mention`, звуки, уведомления/прочтение — подтверждать по серверным событиям и фактическому просмотру; простой приход WS-пакета **не** означает прочтения. Reconnect должен восстановить список и непрочитанное.
- Попытка отправить из старого сектора, старой корпорации, вышедшей Private-беседы или после изменения прав — UI обязан показать отказ без повторной автоматической отправки. UI — не security boundary.
- Не плодить отдельные страницы для космической и планетарной части; одна компонентная модель и общий Chat view.

## 7. Чего проектировщику делать **не нужно**

- Не переписывать `internal/server/web` на React/Vue/Svelte и не добавлять тяжёлую frontend-библиотеку без объективной необходимости.
- Не писать отдельный drag/resize/tooltip/menu/tabs/notification framework. Использовать имеющиеся `ui/*`.
- Не менять глобальный стиль игры, кнопки других модулей, панель кредитов, слот новостей или логику кораблей.
- Не проектировать бэкенд, не писать Go/SQL и не создавать Chat Service «для демонстрации».
- Не копировать историю чата в `localStorage` или `Preferences`; персональные настройки могут быть локальны, но конфиденциальные сообщения/приглашения — из авторизованного backend state.
- Не выдумывать новые игровые правила вместо уже утверждённых 01/02.

## 8. Что **обязан выдать** отдельный чат-проектировщик

**В первую очередь артефакты проектирования, а не изменения исходников:**

1. **Карта повторного использования** точных существующих функций/CSS/элементов `internal/server/web`: какой компонент переиспользуется, какой минимальный extension нужен, почему нельзя обойтись существующим.
2. **Две подробные компоновки**: floating и home-docked, размеры, прямые углы, плотность, шапка, вкладки, сообщения, поле ввода; отдельно указать поведение на узких экранах. Показать wireframe/демонстрацию в чате, если доступная функция позволяет, используя **mock-данные**.
3. **Схема переходов UI** floating ↔ docked, открытие из sidebar, закрытие/возврат, приватные списки, назад, поиск, ошибки, меню сообщений, настройка прозрачности, сохранение scroll/draft.
4. **Точные планы DOM/CSS/JS** (какие существующие файлы и какие новые `features/chat/*` нужны), без создания альтернативной системы окон.
5. **Перечень UI состояний** empty/loading/error/no_connection/no_planet/no_corporation/muted/pending_invitation/active/conversation_deleting/disabled_send, включая подписки и accessibility.
6. **План проверок и скриншотов**: минимум desktop ~1440×900, laptop ~1280×720, tablet ~900px, mobile ~375px; режимы на 100%/пользовательской непрозрачности, chat floating+home, раскрытие Private, переполнение длинных сообщений, 200% zoom, keyboard/touch, RU/EN. Регрессии других модулей и no-scroll/overflow.
7. **Готовый handoff для разработчика**, сохраняемый отдельными MD-файлами в `docs/ideas/chat-service/`, например `15-frontend-layout-design.ru.md`, `16-frontend-behavior-matrix.ru.md`, `17-frontend-codex-handoff.ru.md`. Это **ожидаемые файлы от отдельного чата**, не существующие сейчас; не выдавать их за уже подготовленные. Не переписывать 01/02 без согласования.

## 9. Как передавать результат владельцу

Сначала показать **компоновку в двух режимах** и кратко объяснить, где именно повторно используются существующие компоненты; не требовать от владельца десятков новых ответов. Не добавлять много декоративных деталей, не согласованных с требованием компактности. После доработки макета — оформить MD-спецификацию и передать как handoff Codex.

**Конечная цель:** интегрированный компактный Chat-модуль Cosmosimulator, а не новый продукт/новая верстка рядом со старой.
