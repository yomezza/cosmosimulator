# Chat Service — алгоритмы бизнес-логики и конкурентности

**ВНИМАНИЕ для Codex:** детальный порядок блокировок, state machines, sender idempotency и Private receipts исправлены в [10-state-machines-and-transactions.ru.md](./10-state-machines-and-transactions.ru.md). Применять 10 при расхождении.

Версия проекта 1.0 (2026-10-30). Источники: [01](./01-idea-v1.ru.md), [02](./02-approved-decisions.ru.md), [03](./03-architecture-integration.ru.md), [04](./04-postgresql-design.ru.md). Это техническая спецификация, а не исполняемый код.

## 1. Серверная матрица доступа

| Раздел | Где разрешён | Лимит символов | TTL | Скорость |
|---|---|---:|---:|---|
| Global | все авторизованные | 256 | 30 суток | 1 за 3 секунды |
| Planet | только текущая поверхность при active visit | 256 | 30 суток | 1 за 2 секунды |
| Sector | только текущий канонический сектор при active visit | 256 | 7 суток | 1 за 1 секунду |
| Corporation | действующий участник текущей корпорации; служебное чтение администрации | 256 | 90 суток | 1 за 1 секунду |
| Private | только active участник данной беседы | 500 | 180 суток | 10 за любые 10 секунд |
| Избранное | исключительно владелец | 2500 | бессрочно | обычная защита API |

Все частотные лимиты относятся к **аккаунту и типу раздела**, а не к конкретной планете, сектору, корпорации или беседе: переключением scope обходить cooldown нельзя. В любой операции разрешения проверяются **на сервере**, не в UI. Поиск и read/history не обходят ограничения.

Единый AccessResolver получает actor_id, action, kind, target, свежий снимок службы/членства/visit; возвращает channel и решение; не писать 6 почти одинаковых наборов условий. Чтение/поиск/сохранение копии/жалоба/передача/удаление требуют разных разрешений. Администратор не получает неоговорённый доступ к чужим Private/Избранному. Для Planet/Sector никто не верит browser surface/sector.

## 2. Private: состояния и приглашения

### DM

1. Нет открытой пары → создаётся pending conversation и уникальная canonical пара (min(userID),max(userID)); sender отправляет invite, получателю нельзя читать/писать до accept.
2. Accept до срока → разговор active; двое active members, начальная unread baseline=0. Decline/expiry → pending беседа удаляется, отдельно хранится запись попытки/cooldown.
3. Встречные приглашения A→B и B→A → под блокировкой пары автоматически открывается **один** DM, без двойных бесед или второго согласования.
4. Creator личного диалога приглашает C → invite на conversion. Пока C не принял, A и B продолжают общаться и удалять свои сообщения. После accept C в одной транзакции: conversation type=group, C становится active member, исходная история остаётся в **том же канале** с прежними ID, запись canonical пары удаляется. Второй собеседник НЕ имеет права вето. Старый DM перестаёт быть DM, пара A/B вправе открыть новый отдельный личный разговор.
5. Если до accept C один из A/B вышел, DM удаляется и invite отменяется. Нельзя принять устаревший запрос или восстановить старую историю.
6. Выход любого из двух участников DM → немедленно запретить доступ, удалить беседу/переписку для обоих; повторная переписка начинается только по новому приглашению.

### Group

1. Создатель создаёт pending группу, может менять название и приглашать, но отправка сообщений запрещена до **первого accept**. Первый accept даёт active group из двух игроков.
2. Когда все приглашения ещё pending-группы declined/expired — удаление черновика; техническая защита: пустой draft без единого приглашения GC после 7 суток неактивности, но не станет активной группой из одного.
3. Не более 50 active участников, включая владельца. Техническая безопасная резервация: active + pending invitations не более 50; accept ещё раз проверяет ёмкость.
4. Только действующий owner может invite, kick, rename, transfer owner, delete-for-all. Текущий owner имеет все права, предыдущий после передачи — обычный участник.
5. Добровольный выход владеющего, если группа остаётся (после выхода >=2 участников), требует вручную выбрать нового владельца из active members. Одновременные операции изменения владельца проверяют revision; без назначения выход отказан.
6. Kick/leave немедленно отнимает право читать **всю** историю. Можно вернуться только после нового приглашения от owner и принятия; вся сохранившаяся история снова видима. Ранее saved copies при выходе/исключении сохраняются.
7. Два участника в group — всё ещё group, обратно в DM не преобразуется. После leave/kick, когда остаётся **один**, group и её сообщения удаляются автоматически; owner transfer тогда не нужен.
8. При удалении беседы все pending invites отменяются; сообщения и metadata физически исчезают из активной БД, независимые копии в Избранном остаются. State deleting не даёт позднему accept/send «воскресить» беседу.

### Приглашения, скоростные ограничения

- TTL приглашения — 7 суток. Повтор после отказа тому же recipient в ту же conversation — только через 24 часа; для DM cooldown проверять по canonical паре **после удаления старого pending conversation**, чтобы запрет нельзя было обойти новым ID.
- Одному recipient в одной conversation — не более одного pending приглашения. Одному target от одного sender — **не более 20 действительных попыток отправки приглашений за скользящие 24 часа**, по всем Private вместе. Duplicate retry с тем же request_id квоту не увеличивает.
- Self invite, bot invite, несуществующий пользователь запрещены. Приглашённый принимает/отклоняет только сам; отказ уведомляет автора.

## 3. Атомарные операции и блокировки

Порядок **для Chat-owned объектов**: conversation/pair canonical → members/invites по user ID → channel next_seq → rate rows → locator/message → unread/outbox. Для взаимодействия с Cosmic при корпоративных изменениях согласовать единый lock order на company/users: нынешние company_dissolve и join/leave могут брать строки в разном порядке. До включения чата Codex обязан унифицировать порядок на обеих сторонах либо обеспечить доказанно безопасные транзакционные retries на 40P01 и 40001. Не маскировать deadlock бесконечным retry.

Для DM-пары lock canonical key: запись chat_dm_pairs UNIQUE(min,max) + transaction advisory lock на пару до создания row. Встречные invites сериализуются. Если повтор запроса имеет тот же request_id и payload_digest, возвращается прежний outcome; иной payload → 409 conflict.

- Accept vs expiry: accept с временем БД ранее expires_at и первым COMMIT выигрывает; на/после expires_at принимать нельзя.
- Send vs kick/leave/transfer/delete: только после актуального состояния под lock. Более поздний send получает access_denied или gone.
- Одновременные leave двух участников: один победитель, второй получает already_deleted; не бывает группы из нуля, не оставлять orphan invites.
- Повторное удаление того же channel/корпорации безопасно, не затрагивает другой scope.
- При потере ответа после COMMIT повторить именно **тот же** request_id; без изменения лимитов, seq и числа уведомлений.

## 4. Отправка обычного сообщения

1. Проверить JSON envelope версии 1, Origin/session/cookie, размер фрейма, допустимые поля, UTF-8, типы. Принять request_id UUID, kind/target, plain body, optional reply_to, structured game links/mentions; никогда не принимать actor_id/role/location как полномочие.
2. Проверить readiness Cosmic. Для spatial дополнительно authoritative active visit Planet и fresh epoch; при невозможности подтвердить точный сектор отказ. Проверить права адресатов ссылок и упоминаний.
3. BEGIN SQL tx. Идемпотентность по (actor,request_id) и digest. Под блокировками повторно проверить действующего current member, company mute, не-deleting company/conversation, целевой channel/scope; reply_to должен сейчас существовать и быть доступным в **том же канале**.
4. В той же транзакции взять слот частоты: Global >=3s, Planet >=2s, Sector >=1s, Corporation >=1s; Private не больше 10 событий за rolling [now-10s,now), во **всех** беседах. При откате слот не тратится.
5. Increment chat_channels.next_seq и взять seq; вычислить sent_at и expires_at от DB UTC; INSERT locator + партиционированное сообщение (в том числе номер исходного сектора для Planet; отдельное поле system_data или секторное origin поле должно быть доступно при рендере).
6. Private: для каждого active участника кроме автора увеличить unread_count на 1. Записать outbox с IDs без текста + operation result. COMMIT.
7. Только после COMMIT отправить ACK. Фан-аут WS не является подтверждением сохранения.

Для spatial commit-fence — короткая SQL tx с SELECT ... FOR SHARE по **Planet-owned current-visit row** (только после реализации P2-4+). Проверить state=active, user_id, connection_epoch/current_surface/current_sector, last_presence_at и актуальный runtime lease. Все переходы секторной границы, выход, разрыв и отзыв в Planet обязаны UPDATE ту же строку; конкурентное изменение будет сериализовано этим row lock. Никогда не держать DB tx на HTTP запрос и не использовать нынешнюю legacy planet_visits без этих полей. Пока контракт отсутствует — spatial fail closed.

## 5. Прочтение, упоминания, уведомления

- Private unread_count возникает лишь для сообщений, поступивших **после последнего вступления** участника (join_floor_seq); уже имевшаяся переписка доступна, но не считается непрочитанной.
- Прочтение фиксировать только когда сообщение в видимой области **открытой, активной** беседы, документ видим; клиент отправляет батч IDs (до 100). Receipt по (user,message) уникален, повтор не снижает unread дважды. Автор собственного сообщения в unread не входит.
- «Синяя точка» = существует receipt от хотя бы одного **другого** игрока; это не «прочитали все». После выхода участника старые receipts сохраняются пока жив original; после повторного входа новые receipts допустимы при доступе. Удаление/TTL исходника уменьшает unread у всех затронутых active recipients ровно на число ещё непрочитанных удалённых сообщений; периодическая reconciliation сверяет счётчики с живыми данными и receipt.
- Для Global/Planet/Sector только индикатор новых (high seq vs last_seen_seq), без числового счётчика; старый сектор после выхода не подсвечивается. Corporation также получает индикатор.
- Упоминание адресовано **user_id**, отображаемое имя динамическое. Global: существующий player; Planet/Sector: сейчас присутствующий в соответствующем пространстве; Corporation: текущий member; Private: active member. Не отправлять уведомления тем, у кого нет доступа на момент доставки.
- @all разрешён в Corporation и **в любом активном Private (включая личный диалог)**, запрещён в остальных. Защита от звукового спама: повторные @all от одного sender в одном канале чаще 1 раза в 60 s доставляют сообщение, но не повторяют массовый звук. Для обычного Global/Planet/Sector потокового чата звука нет; персональные упоминания и Private по умолчанию озвучиваются, если пользователь не отключил.
- Уведомления Private и invites/отказы доступны при следующем входе через БД даже при потере WS. Самостоятельный outbox/NOTIFY — ускорение, не гарантия сохранности.

## 6. История, поиск, сообщения-ответы, ссылки

- Read history: последние 50, затем keyset по channel_id + seq; срочно проверять действующий доступ и expires_at>now. В Planet заголовок показывает название планеты, каждое сообщение — **исходный номер сектора** и каноническое название по hover/tap.
- Search во всех шести разделах; только разрешённые сейчас каналы; русский/английский без учёта регистра, подстроки, эмодзи; bounded query <=128 codepoints, timeout, не более 50 результатов на страницу. pg_trgm для большого текста, нельзя сканировать чужие каналы с последующей фильтрацией в JS.
- Reply_to указывает только на оригинал в том же канале. После TTL/deletion/отзыва доступа ответ остаётся, UI пишет «Исходное сообщение недоступно». Не дублировать оригинальный текст в ответе или системном событии.
- Игровая ссылка — типизированная запись (kind,stable_object_id), проверять доступ на вставке и повторно на открытии; никакого arbitrary HTML/javascript: URL. Пользовательские сообщения plain text + Unicode emojis.

## 7. Удаление и Избранное

- Автор удаляет только своё обычное сообщение для всех; сохранённые копии в чужом Избранном остаются. Модератор удаляет чужой original за нарушение, требует причину, **в той же транзакции удаляются все связанные saved copies WHERE source_message_id=ID**. Самостоятельные заметки с похожим текстом не удаляются.
- Lock locator при save-copy и moderation deletion сериализует возможный race: либо копия сохранена раньше и будет удалена, либо сохранение увидит отсутствующий original и получит not_found.
- Избранное хранит независимый текст + автора/ID + исходную дату и source kind/message + planet/sector при наличии + saved_at. Дубли разрешены, note можно менять, copy — нет. Удаление папки делает folder_id=NULL, элементы остаются в виртуальном «Все».
- Удаление Private беседы или corporation: независимые favorites остаются; TTL сообщений не удаляет метаданные Private беседы (если не было отдельного пользовательского delete).

## 8. Корпоративная модерация и жалобы

- Глава может mute любого **другого** участника, включая corporate moderator; moderator с chat.moderate может mute только обычного member; не друг друга/лидера/самого себя. Game admin/game moderator с правом chat.game_moderate обладает служебным доступом согласно утверждённому уровню полномочий.
- Сроки mute только 5 min, 30 min, 1 h, 24 h, 7 days. Запрет писать не запрещает читать/искать и не затрагивает другие каналы. Причина обязательна, хранится только в restricted audit/mute. Досрочно снять может лидер или **любой текущий corporate moderator**, согласно исходной идее; каждое действие журналируется.
- Причину видит адресат, корпоративные модераторы и игровые администраторы/назначенные игровые модераторы. Обычным членам причина не раскрывается.
- У сообщения показывать «…» при hover, на touch/клавиатуре отдельное действие. Контекстное меню: «Сохранить в избранное», «Пожаловаться», «Ответить», «Удалить» при праве. Жалоба требует текущего права читать оригинал и причину; в chat_reports **не копировать body**; 1 открытая жалоба одного автора на один original, антиспам 5 сообщений-жалоб в 10 min (техническое ограничение).
- В Corporation показывать системные события модерации лишь уполномоченным получателям; публичную причину не раскрывать. В Private system events: принял/приглашён/вышел/исключён/переименовал/передал владение. System events не занимают пользовательские rate slots; TTL как у сообщений своего канала.
- Аудит просмотров корпоративного чата игровыми администраторами доступен только уполномоченной игровой администрации; владельцу корпорации скрыт. В журнал не писать текст удалённых сообщений, TTL audit=180 суток.

## 9. UI и отказы

- Один компонент чата для космоса и планеты: фиксированные tabs Избранное, Global, Planet, Sector, Corporation, Private; Private — отдельный список бесед. Последняя разрешённая вкладка и DM; если недоступна — Global. Скрытые Global/Planet/Sector, размер/позиция окна, компактный режим, звуки — персональные настройки.
- При Chat WS loss — статус «Нет соединения»; содержимое поля ввода сохраняется, но после reconnect **не отправляется без нового явного действия пользователя**. Если Cosmic unavailable подтверждённо — все разделы недоступны; если Planet unavailable — только Planet/Sector. При восстановлении заново проверить session, company, presence, unread и invites.
- Ошибка отправки при неизвестном результате (disconnect после commit) не означает неудачу: клиент с тем же request_id делает status/retry или перечитывает канал; сервер возвращает тот же message ID без нового сообщения.
- Никакого автоматического открывания чужого location, повторной отправки черновика или «временного разрешения» по устаревшему кэшу.
