# Границы космической и будущей планетарной служб

Зафиксировано при подготовке M0, 29 октября 2026. Это контракт для последующих этапов, **не утверждение, что разделение уже реализовано**. Сейчас работает космический `cmd/cosmosimulator`, почти все Go-функции находятся в `internal/server`.

## Ответственный за изменяемые данные

| Данные / операция | Ответственный обработчик | Как другой сервер использует данные |
|---|---|---|
| Галактики, системы, гиперкоридоры, космические объекты | Космическая служба | Получает нужные идентификаторы и read model; не запускает собственную генерацию мира |
| География поверхности, материки, океаны, реки, hex-сектора, версия географии | Космическая служба | Планетарная служба читает канонический sector snapshot и его версию; локальная сцена не генерирует другую береговую линию |
| Территории, владельцы, проекты, взносы, возвраты, строительство колонии | Космическая служба | Планетарная служба проверяет доступ через согласованный контракт; не меняет owner/project напрямую |
| Корабли, космический груз, топливо, маршруты, очереди | Космическая служба | Планетарная служба не выполняет второй cosmic tick и не изменяет корабль параллельно |
| Персонажи внутри сектора, движение, локальные объекты, добыча и строительство | Будущая планетарная служба | Космическая служба получает проекцию состояния, не управляет каждым шагом персонажа |
| Персональный инвентарь высадившегося персонажа | Будущая планетарная служба | Обмен с космическим грузом — отдельная идемпотентная операция; не два независимых UPDATE |
| Кошельки, космические склады, межсервисный обмен ресурсами | Существующий обработчик экономики до отдельного согласования | Второй сервер отправляет команду владельцу. Один баланс нельзя поручить двум независимым tick loops |
| Пользователи, сессии, роли, корпорации | Существующие обработчики доступа/корпораций | Вторая служба проверяет авторизацию на сервере; доверие к browser role/token contents без валидации запрещено |
| Миграции общей PostgreSQL | Один назначенный migration runner | Обычный запуск второго процесса не должен повторять космический bootstrap/seed/upgrade |

Общая PostgreSQL не означает общий набор прав записи. При реализации второй службы нужны отдельные DB roles и явно перечисленные права, а также транзакционные инварианты. Общие идентификаторы planet/surface/sector/colony не дублируются локальными несогласованными ID. Планетарная служба может оставаться недоступной, пока космический терминал продолжает работать; состояние открытия сектора и ошибки подключения должны отображаться отдельно.

## Что можно выделять для повторного использования

1. Узкую инфраструктуру PostgreSQL: разбор DSN, проверку и quoting `DB_SCHEMA`, конфигурацию pool/search_path, deadlines и закрытие соединений. Это кандидат на общий пакет, а не повод импортировать `server.App` из второй службы.
2. Небольшие стабильные типы идентификаторов и DTO канонической географии с version contract. Не экспортировать всю внутреннюю модель симуляции только для удобства импорта.
3. Чистые функции geography sampler/координат — только если другой потребитель реально использует тот же алгоритм и версию. Генерация/изменение сохранённой планеты остаётся у космического владельца.
4. Узкий транзакционный интерфейс (`Exec/Query/QueryRow` или интерфейс конкретного use case) там, где нужна одна транзакция. Нельзя скрыть внутри helper новый pool/transaction, когда вызывающий уже держит блокировки.

Общие пакеты не импортируют composition root, HTTP handlers, игровой tick или frontend. Подключение к БД, migration/seed и запуск simulation должны стать отдельными действиями. Сейчас `openDatabase` выполняет и подключение, и инициализацию/upgrade; **повторно использовать его во втором сервере в текущем виде нельзя**.

Не создавать заранее большой `shared/utils/common` с SQL всех подсистем. Сначала выделяется конкретный существующий механизм с тестами, затем подключается реальный второй потребитель. До этого серверный перенос выполняется отдельным этапом и не смешивается с frontend M0/M1.

## Передача управления между службами

Высадка/возвращение должны иметь operation ID, однозначное состояние визита и защиту от повторения. Межпроцессные блокировки/ограничения PostgreSQL, version/revision и восстановление после crash важнее process-local mutex. Нельзя надеяться на mutex космического процесса для защиты от планетарного процесса.

При изменении geography существующей планеты старая локальная локация не продолжает работать по прежней географии без проверки revision/доступа. Invalidation через LISTEN/NOTIFY может ускорять обновление, но не заменяет сохранённую версию. Новые tables/permissions/handoff API и их миграции будут проектироваться отдельно, с тестами конкурентных писателей и повторной доставки команд.

## Проверки перед выделением общего DB-пакета

- Неизменный search_path для всех pool connections, quoted schema, отсутствие fallback в чужой `public`.
- Сохранение существующих транзакций/lock order и миграционных гарантий.
- Подключение читателя не вызывает seed, генерацию галактик, тик или upgrade.
- Космический и планетарный DB roles не могут писать в чужие authoritative tables.
- Повторная высадка/возвращение/передача груза не начисляет деньги или ресурсы дважды.
- Остановка планетарной службы не делает недоступными космические routes.

Эти проверки — требования будущих этапов; M0 не объявляет их уже выполненными.
