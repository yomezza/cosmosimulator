# Постоянные локальные сцены · P2-3 / 0.17.0

Планетарная служба получила repository сцен, генератор природного декора и ограниченный кеш загружаемых секторов. Геометрия и объекты сохраняются в PostgreSQL и восстанавливаются после перезапуска. **Персонаж, авторизованный вход в 2D, Canvas и управление ещё не подключены**: следующий этап — P2-4. Публичного API для получения произвольной чужой сцены нет.

[Полный отчёт и проверки](REPORT.ru.md) · [Согласованная последовательность](../P2-0/PLAN.ru.md) · [Предыдущий результат P2-2](../P2-2/REPORT.ru.md).

## Обновление

1. Остановить обе службы и сохранить согласованную резервную копию игровой схемы PostgreSQL.
2. Запустить **cosmosimulator 0.17.0** с прежними DATABASE_URL / DB_SCHEMA. Только cosmic runner создаёт `planet_local_locations` и повышает совместимость до **3**. Генерации всех секторов при миграции нет.
3. Выдать планетарной роли дополнительные права из раздела ниже.
4. Запустить **cosmosimulator-planet 0.17.0** на той же БД/схеме. Readiness возвращает `stage=P2-3`, `status=ready`, `gameplay_ready=false`.

Старые EXE сохранены в downloads. Службы разных версий нельзя смешивать: planet 0.16.0 откажется работать с marker=3. Старый cosmic не знает порядок очистки локальных сцен. Для отката остановить planet и использовать согласованную резервную копию с соответствующими сборками.

Общий запуск и Windows SCM: [инструкция второй службы](../P2-1/README.ru.md). Конфигурация читается из окружения процесса/службы; `.env` автоматически не читается.

## Права PostgreSQL

Пример для схемы `cosmosimulator` и заранее созданного оператором login `cosmos_planet`. Выполнить оператором после миграции; заменить имена с корректным SQL quoting:

```sql
GRANT USAGE ON SCHEMA cosmosimulator TO cosmos_planet;
GRANT SELECT ON cosmosimulator.planet_schema_state,
                cosmosimulator.planet_runtime_leases,
                cosmosimulator.planet_local_locations,
                cosmosimulator.planet_surfaces,
                cosmosimulator.planet_surface_controls,
                cosmosimulator.planet_runtime_controls,
                cosmosimulator.planet_colonies,
                cosmosimulator.planet_projects,
                cosmosimulator.planet_landing_sites TO cosmos_planet;
GRANT UPDATE (owner_id, fence, expires_at)
  ON cosmosimulator.planet_runtime_leases TO cosmos_planet;
GRANT INSERT, DELETE ON cosmosimulator.planet_local_locations TO cosmos_planet;
```

UPDATE локальных snapshot не нужен: они неизменяемые. Последовательность для новой таблицы не требуется. Не выдавать planet изменение кошельков, кораблей, колоний, площадок, surface controls и marker; CREATE/DDL также не нужен. Отдельные роли/пароли приложение не создаёт. При общем административном DATABASE_URL разграничение остаётся правилом кода, а не ограничением DB.

## Настройки кеша

| Переменная | По умолчанию | Допустимо |
|---|---|---|
| PLANET_SCENE_CAPACITY | 32 сцены, включая ожидающие загрузки | 1–1024 |
| PLANET_SCENE_IDLE_TTL | 2m после освобождения последней ссылки | 1s–1h |
| PLANET_SCENE_LOAD_TIMEOUT | 20s на одну общую загрузку | 1s–1m |

Тяжёлые холодные загрузки выполняются максимум по две одновременно. Загрузка одного ключа объединяется для всех ожидающих. При полном кеше удерживаемые сцены не вытесняются: новый запрос получает явный отказ по ёмкости. После простоя освобождается только RAM, сохранённый snapshot остаётся в PostgreSQL. Ожидание конкретного клиента можно отменить без отмены общей загрузки остальных клиентов.

Настройки подключения, lease, Origin и shutdown из P2-1 сохраняются. Здесь нет симуляционного цикла на каждый пустой сектор, записи координат на каждый кадр или массовой предварительной загрузки графики.

## Удаление и перегенерация поверхности

Прежние проверки высадок, возвратов, вкладов и подтверждения сохраняются. Если локальных сцен ещё нет, операция выполняется как прежде.

Если сцены уже сохранены, первая подтверждённая операция переводит surface control в `retiring`, записывает действие администратора и отвечает **409 с пояснением подготовки**. Новые загрузки запрещаются; planet дожидается освобождения ссылок и своим writer удаляет локальные snapshot. После этого администратор **повторно открывает предупреждение и подтверждает операцию**: cosmic удаляет глобальные зависимости и меняет revision. Между шагами исходная география и финансовые записи остаются на месте.

Планетарная служба должна работать для очистки. При её остановке/ошибке БД подготовка остаётся ожидающей; cosmic не подменяет planetary writer и не удаляет данные через CASCADE. После начала подготовки новые 2D-входы остаются закрытыми до завершения удаления/перегенерации. В P2-3 живых персонажей ещё нет; в следующих этапах этот барьер будет дополнен состояниями визитов и handoff.
