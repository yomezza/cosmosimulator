# Отчёт P2-6 · 0.20.0

Дата: 30 октября 2026. Реализованы видимость других персонажей в локальной сцене, поток состояния WS v1, ограниченное восстановление соединения и административное окно статуса двух служб. География/immutable сцены и экономика сохраняют прежних владельцев.

## Видимость и движение

В `planet_characters` добавлен уникальный публичный UUID: это постоянная идентичность персонажа, отдельная от account DB ID, временного визита и connection epoch. Он сохраняется при resume, повторной высадке и перезапуске. Узкое session view теперь возвращает также игровое имя; пароль/кошелёк в него не добавлены.

`movement.Hub` собирает неизменяемый список персонажей каждого активного сектора примерно 10 раз в секунду. Один actor loop сектора по-прежнему считает движение в RAM с шагом 50ms. Присутствие не требует SQL на каждый frame. Другой сектор не входит в выборку. Когда последний controller уходит, loop останавливается.

Браузер получает `welcome`, начальный `sector.snapshot`, `actor.enter`, `actor.leave`, `state.delta`, собственный accepted path. У каждого серверного пакета есть монотонный `server_seq`; визит и epoch остаются обязательными после активации. В публичном персонаже только UUID, имя, sprite, координаты, movement flags и время. Чужие пути, роли, аккаунтные ID и сессии не передаются.

Canvas сортирует всех видимых персонажей вместе с декором по Y опоры. Игровое имя рисуется обычным текстом, вокруг опоры — устойчивый цвет по публичному UUID. Позиции других игроков интерполируются с задержкой примерно 100ms без экстраполяции. Скрытая вкладка не рисует scene; серверная физика продолжает работать. Использован прежний PNG колониста — анимация восьми направлений остаётся P2-8. [Два персонажа](checks/preview.png).

## Ограничение очередей

У controller два буфера по одному элементу: последний собственный state и последний полный membership frame. Старый кадр заменяется новым. Enter/leave вычисляются относительно состава, который конкретный WS writer уже успешно отправил. Поэтому пропуск промежуточных frames не оставляет вечного «призрака» и не требует неограниченной reliable event queue. При полном resync база состава заменяется; более старый queued frame пропускается по sector sequence.

Один writer упорядочивает события. Deadline 3s относится ко всему batch появления/ухода/дельты, а не отдельно к каждому персонажу. Реально остановившийся читатель закрывается. Ping каждые 15s, Pong timeout 5s обслуживается отдельным reader. Лимиты входа 4KiB и 10/s с burst20 сохранены; resync ограничен 1/s, не принимает чужой sector или отрицательный seq. [Реализованный протокол](PROTOCOL.ru.md).

## Восстановление и checkpoints

Браузер обнаруживает отсутствие frames >6s, закрывает старую связь и делает resume авторизованного визита. Exponential backoff/jitter, до восьми попыток и проверка окна 60s перед очередной попыткой. После лимита — ручной повтор либо возврат. Успешная стабильная связь 10s сбрасывает попытки. Полный reload тоже читает текущий visit, не создавая новую независимую высадку.

`session_replaced` прекращает автоматический перехват: две вкладки не борются бесконечно. Auth/access/visit/version отказы также прекращают автоматическое подключение. Закрытие окна/logout отменяет таймеры, запросы, renderer и WS; поздний PNG/snapshot не возвращает закрытый controller.

Позиция сохраняется только при изменении, с интервалом 5.0–5.5s для небольшого разнесения аккаунтов, а также при takeover, disconnect, возврате и остановке. Сохранение каждого пользователя остаётся короткой отдельной tx с проверкой session, прав, world lock, runtime lease/fence, connection epoch, generation и CAS версии позиции. Между HTTP/WS ожиданиями SQL-транзакция не удерживается. Полное пакетирование/характеристики нагрузки проверяются на P2-9, а не объявляются решёнными одним таймером.

При потере БД разрешение actor на движение само истекает за 2s; ошибки проверок закрывают связь. Новый runtime после fence/expiry загружает последний подтверждённый checkpoint, а не принимает координаты от клиента. Несохранённые секунды при аварии могут потеряться. Исправлено освобождение actor на границе входа: defer disconnect использует fence успешной активации; потеря lease сразу после commit больше не оставляет actor без cleanup.

## Статус служб

**Панель администратора → Статус служб** открывает две карточки: название по центру, контурный тег, горизонтальная линия и технические сведения. Проверка раз в 5s, только пока окно открыто. Доступ проверяет cosmic API, а не только скрытая кнопка; обычный игрок получает 403, неавторизованный запрос — 401.

Космическая карточка показывает версию, uptime, Go/платформу, pool PostgreSQL, схему и время ответа. Планетарная — адрес конфигурации, readiness HTTP/задержку, версию/этап/схему. Для зелёного тега дополнительно сверяются runtime identity, fence и свежая lease с **этой** игровой БД. Просто запущенный HTTP-процесс или готовая служба с другой БД не дают ложного «Готова».

Отдельные состояния для disabled, отсутствия связи, неготовности/lease, некорректной настройки и другой игровой БД. У причины есть RU/EN пояснение. Probe имеет timeout, ограниченный JSON, не пересылает cookie и не следует redirects. Endpoint берётся исключительно из `PLANET_INTERNAL_URL`, credentials/query/fragment/path в нём запрещены. DATABASE_URL, password/session tokens в API отсутствуют. При недоступности самого cosmic окно показывает ошибку обновления; внешний мониторинг оно не заменяет. [Карточки интерфейса](checks/services-preview.png).

## Схема и rollout

`schema200.sql` повышает marker до 6, добавляет `public_id` и nickname в session view. Новых экономик, генерации географии, scene format или writer глобального tick нет. Схема обновляется только cosmic migration runner. Старый шаг создания view исправлен: повторный прогон не пытается удалить добавленную позднее колонку, что запрещает PostgreSQL.

Существующие GRANT уровня таблицы/view P2-4 достаточны. Установки с вручную ограниченными column grants дополняются соответствующими колонками. [Порядок обновления двух EXE](README.ru.md): остановить обе службы, обновить, сначала cosmic, затем planet. Старые сборки сохраняются; rollback — с соответствующей резервной копией схемы.
