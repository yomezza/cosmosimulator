# P2-6 · мультиплеер и восстановление · 0.20.0

Теперь несколько авторизованных игроков видят друг друга в одном секторе. Есть имена, плавное движение, появление/уход и ограниченное автоматическое переподключение. Нужны собственная завершённая колония или право `planetary.enter`, исследованная система и корабль у планеты — правила P2-4 остаются.

## Обновление

1. Остановить планетарную и космическую службы. Сохранить резервную копию общей БД/схемы.
2. Заменить оба EXE на `cosmosimulator-v0.20.0-windows-amd64.exe` и `cosmosimulator-planet-v0.20.0-windows-amd64.exe` из `downloads` либо GitHub Release. Старые EXE сохраняются.
3. Запустить cosmic: единственный migration runner применит `schema200.sql`, добавит постоянный публичный UUID персонажа, расширит узкое session view игровым именем и повысит marker до 6. Повторный запуск не удаляет колонку view. География/scene format не меняются.
4. Запустить planet с прежними `DATABASE_URL`, `DB_SCHEMA`, Origin allowlist и параметрами P2-4/5. Ожидаемая схема — 6; смешанные версии служб не использовать.
5. Readiness `/planet/api/v1/health/ready` должен вернуть 200, `stage=P2-6`, `gameplay_ready=true`, `multiplayer_ready=true`, `landing_ready=true`.

Новых таблиц/GRANT не требуется при прежних правах P2-4: `SELECT ON planet_session_lookup` включает добавленное имя, а `INSERT,UPDATE ON planet_characters` — новую колонку. Роль только с GRANT на отдельные колонки нужно дополнить `public_id` и `nickname`. Planet не выполняет DDL, не создаёт пользователей/галактики и не меняет world tick.

## Пользователю

ЛКМ — идти, колесо — масштаб, ПКМ/средняя кнопка — обзор. Другие персонажи показаны исходным спрайтом колониста; рядом имя и цветной контур. Один публичный UUID сохраняется между визитами, цвет стабилен. Видимость ограничена текущим сектором; столкновения игроков между собой пока не добавлены.

При разрыве окно перестаёт управлять персонажем и показывает восстановление. До восьми попыток с возрастающей задержкой/jitter, максимум примерно минута; после этого доступны «Продолжить высадку» и «Вернуться в космос». Если управление перехвачено другой вкладкой, автоматического обратного захвата нет. Явное нажатие «Продолжить» заменяет controller обычным авторизованным resume.

После сбоя БД/процесса восстанавливается подтверждённый checkpoint. Последние несохранённые секунды могут быть потеряны; скорость камеры/браузера не влияет на расчёт позиции. Недоступные площадки/отозванные права не обходятся восстановлением.

## Статус служб для администратора

В верхнем меню **Панель администратора → Статус служб**. Каждой службе соответствует отдельная карточка с названием по центру, контурным тегом и техническими сведениями под горизонтальной линией. Обновляется раз в 5 секунд, закрытое окно не опрашивает сервер.

Для cosmic: версия, время работы, платформа/Go, занятые/максимальные соединения PostgreSQL, схема и время ответа БД. Для planet: внутренний адрес, HTTP readiness/задержка, версия/этап, версия схемы, поколение runtime и подтверждение, что он удерживает lease именно этой игровой БД/схемы. Одного ответа HTTP 200 недостаточно для зелёного тега.

Состояния: **Готова**, **Отключена** (`PLANET_ENABLED=false`), **Нет связи** (нет ответа), **Не готова** (БД/схема/lease), **Ошибка настройки** (некорректный endpoint), **Другая игровая БД** (отвечает чужой runtime). Под тегом будет пояснение. Проверка использует `PLANET_INTERNAL_URL` космической службы; порт/адрес из браузера не принимается. Только администратор может читать `/api/admin/services`; пользовательская cookie не пересылается во внутренний health-запрос, HTTP redirects запрещены. При недоступности самого cosmic интерфейс сообщает, что статусы обновить нельзя: это окно не заменяет внешний мониторинг.

Следующий этап P2-7 — подтверждаемые переходы между соседними секторами. Анимация ходьбы и финальные текстуры — P2-8; измерение 50 клиентов — P2-9. Эта версия не заявляет завершение этих этапов.

Откат EXE на предыдущую схему выполняется вместе с соответствующей резервной копией; текущий marker не понижать вручную.
