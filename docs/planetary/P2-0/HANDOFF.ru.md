# Высадка, возвращение и восстановление — проект контракта

## HTTP космического владельца

Новые endpoints (ещё не реализованы):

- `GET /api/planet/landing-sites?surface=<id>` — доступные площадки, surface/revision, сектор, публичное имя владельца и причины недоступности. Не раскрывает секрет генерации или состав чужой сцены.
- `POST /api/planet/handoff` `{operation, landing_site, ship}` — начало высадки. IDs передаются десятичными строками, operation — UUID; никаких x/y, role, owner от клиента.
- `GET /api/planet/visit` — авторизованное восстановление состояния только текущего пользователя: reservation/pending/active/return_pending/none, публичный visit ID и endpoint.
- `POST /api/planet/return` `{operation,visit}` — запрос безопасного возвращения/отмены передачи; не UPDATE чужой таблицы visits.

В существующем `planet/action land` нельзя оставить свободную высадку в произвольный проект. Предлагается вернуть понятный `landing_site_required` и открыть выбор площадки вместо старого stub. Старый `leave` после переключения направляет в единственный новый return flow; он больше не DELETE-ит runtime visits.

## Подготовка билета

Cosmic в короткой транзакции существующего порядка блокировок:

1. Проверяет текущую account session, research visibility, completed colony и enabled площадку с актуальной revision. Личная colony — свой owner; corporate — CompanyAccess с `planetary.enter` (owner наследует доступ по существующим правилам). Незавершённые/свободные/чужие сектора запрещены.
2. Космический владелец завершает наступившие манёвры прежним механизмом, затем проверяет именно выбранный принадлежащий пользователю ship: нужная star, NearObject `planet-N`, отсутствие destination/local_target. Нахождения просто в системе недостаточно.
3. Проверяет живой визит/передачу, резервирует конкретный ship в planet_transfer_controls. Корабль не меняет положение. Все cosmic mutators маршрута/портала/эвакуации/планировщика/admin teleport проверяют reservation; нельзя обойти его сменой активного корабля. Остальным флотом можно управлять.
4. Создаёт ticket с криптографическими 32 random bytes, хранит только SHA256, TTL 60 s, user, исходную session, operation digest, landing_site, ship, generation и revision.
5. Возвращает `{operation,ticket,expires_at,endpoint,protocol:1}`. Ticket не помещается в URL, localStorage или логи. Ответ private/no-store.

Повтор operation с другим телом — 409. Если ответ с секретом потерян и билет ещё не использован, cosmic под теми же блокировками может перевыпустить token_hash, аннулируя предыдущий секрет. Если билет уже использован, возвращается состояние визита для **resume**, а не второй билет/новая высадка. Сервер не обязан хранить секрет в открытом виде ради повторного ответа.

## Активация на planet

Клиент открывает WS и в первом hello передаёт ticket. Planet проверяет Origin и существующую session cookie, затем в одном tx:

- Проверяет hash/TTL/revoked_at, привязку к session/user, текущие control generation, revision и enabled площадки.
- Повторно читает canonical права и неизменённые условия ship; сам не settle-ит и не сохраняет корабль.
- Проверяет runtime lease/fence, отсутствие независимого активного визита; загруженная сцена уже подготовлена без долгих блокировок.
- Выбирает серверную безопасную точку рядом с площадкой, создаёт/актуализирует character и visit, выполняет UNIQUE INSERT handoff use. Всё коммитится вместе; сбой не оставляет «полубилет».

Исходный secret после использования больше не даёт новый визит. Использование билета и управление персонажем — разные этапы. `handoff_uses.visit_id` — идентификатор результата операции; журнал uses сохраняется и после замены единственной текущей строки visits, поэтому не имеет FK на изменяемый visits.visit_id.

## Отключение и другая вкладка

Один персонаж и один текущий visit на user. Новое авторизованное соединение с тем же visit атомарно увеличивает connection_epoch; предыдущий controller отключается. Epoch/fence входят в принятые команды и условные записи. Mutex в RAM ускоряет работу, но не даёт вторую независимую сессию после перезапуска.

Resume использует действующую account session + visit ID, а не повторно погашает ticket. Повторно проверяются права, география, контроль допуска и runtime lease. Восстанавливается последняя безопасная позиция, не площадка и не произвольные координаты клиента. После reconnect сразу полный snapshot; старые seq/пакеты игнорируются.

После простого сетевого разрыва visit становится disconnected, персонаж убирается из live присутствия, сохранённая позиция остаётся. Визит не превращается в автоматический новый land. Reservation корабля сохраняется до возвращения/безопасного завершения. Истёкший неиспользованный ticket освобождает reservation после проверки отсутствия use под блокировкой.

## Возвращение

При обычном WS leave actor останавливает движение, сохраняет безопасную позицию и переводит visit в ended с причиной. Cosmic читает committed результат и освобождает reservation своего control. Никаких перемещений ship или выдачи ресурсов.

Альтернатива, если WS пропал: cosmic return записывает revoke request/новое поколение допуска в собственный control, UI показывает «Завершаем высадку». Planet обнаруживает отзыв, перестаёт принимать движение и завершает свой visit; после подтверждения cosmic освобождает корабль. В худшем случае задержка обнаружения равна интервалу проверки допуска (~2 s), не бессрочному кешу. Потеря корпоративного права/logout действует так же. Перед переходом/записью проверка всегда свежая.

Если процесс упал, cosmic не зависит от его HTTP для каждого шага восстановления: после истечения DB lease runtime и fencing предыдущего поколения допуска можно безопасно освободить reservation. Просроченный процесс не сможет записать checkpoint или возобновить старый визит; при рестарте planet приводит оставшуюся строку visits к ended/recoverable по актуальному control. До подтверждения/fencing корабль не отпускается преждевременно.

Действующая сессия в другой вкладке не получает права одновременно управлять тем же персонажем и лететь на закреплённом ship. Это сознательное новое ограничение второй очереди; ручное закрытие окна 2D не равно выходу из визита. В интерфейсе должны быть доступны resume и «Вернуться на корабль».

## Общие гарантии

Нет пароля в handoff. Ticket/operation не принимают роль из браузера. Все записи при возврате/переходе условны по generation/connection_epoch/runtime fence и повторяют результат операции без второго перемещения. DB-ошибка не трактуется как успешный выход. Во время неопределённого результата клиент запрашивает /visit, а не генерирует бесконечные новые высадки.

Legacy visits из первой очереди показываются как незавершённая старая запись без позиции. Они не создают персонажа автоматически. Явный возврат через control и безопасное закрытие runtime снимает её; при отсутствии lease возможен fenced recovery. Это не сброс финансирования/владельца и не новое появление рядом со случайной площадкой.
