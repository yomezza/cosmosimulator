# Локальная сцена, география и движение

## Координаты

Предложение v1: техническая область 256×256 игровых единиц, pointy-top hex внутри неё. Для центра канонического сектора C:

`planetX = C.x + (localX - 128) / 128`

`planetY = C.y + (localY - 128) / 128`

Радиус hex равен 128 локальных единиц. Маска: `abs(dx) ≤ sqrt(3)/2` и `abs(dy) ≤ 1-abs(dx)/sqrt(3)` для dx/dy в координатах планеты. Прямоугольные углы не являются игровой территорией. Никакого растяжения разных сторон hex до одинаковых соседств.

Позиции постоянного состояния — целые q=1/1024 единицы; сетевой x/y также q, клиент переводит в float для отображения. Условная навигационная клетка 1×1; визуальная квадратная сетка не рисуется. Предлагаемый базовый масштаб 16 logical px на единицу при zoom=1; камера не меняет физическую геометрию. Это не физические метры планеты.

## Один канонический источник

Читаем сохранённый PlanetSurface по surface id, проверяем format/revision/checksum. `Sample` даёт высоту/воду, saved sector biome — распределение декора. Не вызываем geography.Generate для локального визита. Planet seed/секрет геологии не передаётся клиенту.

Для воды v1: непроходимы океан/озеро из Sample и полоса вдоль сохранённых Rivers. Нужен общий pure adapter `WaterAt` с версией river-mask и фиксированной шириной 0.04 world units, согласованной с существующим overview stroke. Вычисление distance-to-polyline, без нового генератора рек. Overview и локальный renderer используют эту же маску/контракт толщины. Это уточнение визуального/навигационного чтения уже сохранённых данных; высоты и полилинии не переписываются. Если понадобится другая толщина — новая явно управляемая версия, а не молчаливое обновление старых сцен.

На соседней границе берём одни и те же planet-space samples и одинаковую политику quantization. Проходимость проверяется с учётом диска персонажа, а не только центра клетки. Пересечение в одной точке и проход уже диаметра персонажа не считаются порталом. Ключ общей стороны строится по упорядоченной паре sector IDs; порядок её концов канонический.

## Подготовка локации

1. Зафиксировать source snapshot/revision, local_generator_version, walk_policy_version и приватный decor_seed; прочитать сохранённые cosmic landing sites.
2. Вычислить hex, height/water mask, опорную dry-component, порталы. Эту часть pure terrain используют и cosmic reconciler, и planet runtime.
3. Для каждого разрешённого портала определить устойчивый путь к опорной области. Выделить reserved corridors и область площадки/spawn. Предварительные коридоры не являются дорогами/постройками и не меняют ландшафт.
4. Разместить растения/камни стабильным PRNG и устойчивым порядком попыток. Не использовать текущее время, порядок обхода map Go или renderer FPS. Дерево блокирует основание, не всю крону; трава декоративна. Кусты классифицировать явно. Никаких ресурсов/рубки/шахт как действующих механик.
5. Проверить все коридоры и безопасную область; сохранить immutable packed geometry и checksum. Конкурентное создание разрешает UNIQUE location key и проверка source revision перед commit. Тяжёлая генерация не держит SQL tx.

Политика изменения декора не меняет старые версии. Природные ID выводятся из location + generator version + номера устойчивого слота; DTO содержит public ID/type/position/asset. Умышленно не создаём сейчас таблицу предметов или изменяемых запасов.

Площадка принадлежит cosmic: полученные coords учитываются как неизменяемое reserved место. Если версия не совпала — отказ подготовки, а не перемещение модуля runtime-ом. Старый snapshot не подменяется новым под живым персонажем.

## Навигация и симуляция

A* на 8-связной сетке с запретом diagonal corner cutting. Маска расширяется на радиус персонажа (стартовый ориентир 0.625 единицы), сегменты сглаживания повторно проверяются sweep/collision. Finite q-координаты, hex bounds, достижимость и бюджет расширенных узлов проверяет сервер. Цель в воде/препятствии отклоняется явным reason; произвольная телепортация к «ближайшей» точке не заменяет отказ.

Скорость v1 — серверный config, первоначально 4 единицы/s. Интервал симуляции 50 ms; клиентские команды меняют только цель. При отставании сервера dt ограничен; не выполняем гигантский скачок за пропущенные секунды. Отправка ~100 ms, интерполяция клиента примерно на один сетевой интервал; это параметры для измерения P2-9.

Rate limit намерений, дедупликация seq, ограниченная очередь A* и замена устаревшей цели исключают ускорение спамом. При изменении цели увеличивается path generation, результат старого расчёта не применяется. Планировщик космической добычи в этот цикл не вызывается.

Персонажи пока не являются жёсткими препятствиями друг для друга: это предотвращает блокировку входа группой из 50 игроков и не добавляет новую боевую механику. Spawn выбирает свободные визуальные слоты по возможности, но всегда проверяет статические коллизии/воду.

## Runtime, сохранение, переход

Один actor на **активный** сектор и registry с single-flight загрузкой; пустые сцены не тикают. Registry сериализует вход/idle eviction, refcount/reservation удерживает destination во время перехода. Idle eviction сохраняет данные, затем сверяет отсутствие нового входа. Ошибка сохранения не уничтожает ещё незафиксированное состояние.

Checkpoint каждые 5 s, на выходе/смене сектора/остановке, с CAS по visit/connection_epoch/runtime fence/control generation. Позиции в RAM не являются самостоятельной постоянной БД. При DB outage управление приостанавливается, клиент видит проблему; нет обещания сохранить каждый последний кадр после crash.

Переход: сервер предлагает конкретный neighbor и portal/nonce с TTL. До confirm персонаж остаётся у границы. Destination загружается заранее; заново проверяются owner/доступ/revision. В одном tx фиксируются старая безопасная позиция и новая текущая location у парной границы. Только после commit actor отдаёт despawn исходному сектору и spawn новому. Повтор confirm возвращает ту же операцию, не второе перемещение. Ошибка загрузки/tx оставляет игрока в исходном секторе. После cancel предложение не появляется каждый кадр: нужно выйти из edge zone либо выбрать её снова.

## Рендер

Canvas 2D, кеш статического terrain, UV в глобальных координатах поверхности, маски биомов/воды программные. Сортировка по Y точки опоры; персонаж/растения/площадка отдельные элементы. Крона может перекрывать персонажа визуально, но коллизия у ствола. При необходимости выделение/небольшая прозрачность перекрывающего декора — presentation.

Использовать атлас, не загружать одновременно 56 отдельных frames и его копию. Не грузить base habitat/solar/container/mine, раз эти механики исключены из P2. LRU ограничивает декодированные картинки; статистику памяти и fps измерить при 50 персонажах. Wheel zoom меняет camera transform, ЛКМ задаёт цель, клавиатура — только UI. Camera follows character с плавным offset; масштаб не влияет на скорость/координаты.
