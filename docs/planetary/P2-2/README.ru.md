# P2-2: связанные территории и посадочные площадки · 0.16.0

Космический сервер теперь подготавливает стартовую посадочную инфраструктуру завершённых колоний. На глобальной карте поверхности видны площадки и обслуживаемые ими сектора. **Персонажи, локальная 2D-сцена и настоящая высадка пока не подключены** — это следующие этапы.

## Правила

- Связанная территория состоит только из завершённых колоний одной планеты с одинаковым owner key: отдельно личный игрок, отдельно корпорация.
- Общей стороны гексов недостаточно: проверяется сухой проход через сохранённую географию и реки. Доля суши в процентах не заменяет проверку.
- Для первого отдельного участка создаётся одна площадка. Соседний проходимый сектор расширяет территорию без новой.
- Отдельный удалённый участок получает свою площадку. Если новый сектор соединяет территории, все прежние площадки сохраняют ID и координаты, дополнительная не создаётся.
- После разделения компонента без площадки получает одну безопасную, если есть место. При невозможности размещения выводится причина; вода/берег не переделываются.
- Старые колонии проходят тот же повторяемый backfill. Ресурсы, colony_core, проекты, владельцы и счета не пересоздаются и повторно не оплачиваются.

## Что видно игроку

На hex-карте значок `⇣` отмечает модуль: зелёный — доступный по владению/правам, серый — недоступный. В карточке сектора показываются изображение площадки из предоставленного артпака, владелец и состояние. У присоединённого сектора есть кнопка перехода к сектору с обслуживающим модулем; число секторов территории также отображается. Состав чужих связанных территорий и локальные координаты API не раскрывает.

Подготовка идёт в фоне после завершения колонизации. Во время неё отображается «Подготавливаем посадочную инфраструктуру». После создания владелец/участники с правом посещения получают одно уведомление с планетой и сектором. Из уведомления можно открыть поверхность.

Доступность площадки здесь означает подготовленную инфраструктуру и права, **не готовность 2D-геймплея**. Planet health по-прежнему возвращает gameplay_ready=false. Прежнее информационное окно высадки первой очереди сохранено до подключения нового handoff; отдельное корпоративное право проверяется уже и в этой старой команде. Выбор площадки с одноразовым билетом придёт в P2-4.

## Корпоративное право

В редактировании ролей добавлено `planetary.enter` — «Посещение планетарных территорий». Оно не выдаётся вместе с colonize. Владельцу корпорации доступ положен по существующим правилам CompanyAccess; остальные получают его через роль. Администраторская игровая роль сама по себе не даёт посещение чужих корпоративных владений.

При отзыве разрешения следующее чтение карты и команда визита используют актуальные права. Активных 2D-персонажей пока нет, поэтому механизм их принудительного возвращения будет реализован вместе с визитами P2-4/6.

## Как работает обработчик

Вставка/изменение/удаление canonical planet_colonies помечает поверхность dirty в той же транзакции через schema-scoped trigger. Строительный tick не считает 256×256 и не ждёт второго сервера.

Cosmic worker обрабатывает одну очередь раз в секунду. Коротко читает repeatable snapshot, затем вне world lock строит dry-components/граф и подбирает площадки. Перед записью берёт прежний lock 784218 и сверяет claims/layout epochs и revision. Вставки и уведомления пакетируются pgx.Batch. Несогласованный результат отбрасывается; UNIQUE colony и CAS layout_epoch защищают от двух workers. Dirty queue переживает перезапуск.

Успешная подготовка фиксирует processed_epoch. Неразмещаемые компоненты сохраняют явные issues с повтором через 60 секунд, временная ошибка — через 15 секунд. Budget одной задачи 20 секунд. Никаких независимых INSERT площадок от planet runtime. Cosmic продолжает подготовку, когда второй процесс выключен.

В секторе с несколькими сухими островами опорной является наибольшая связная область; только достижимые из неё порталы участвуют в графе. Это согласованная консервативная политика P2-0. Декор ещё не размещается; будущий генератор должен сохранять проходы и область площадки свободными. Глобальная география не менялась.

## Миграция и запуск

1. Остановить обе службы и сохранить резервную копию игровой схемы.
2. Обновить **оба EXE до 0.16.0**, сначала запустить cosmic с прежними DATABASE_URL/DB_SCHEMA.
3. Его migration runner применит schema160.sql: две новые таблицы, уникальный индекс, dirty trigger и однократную очередь старых колоний. Общая planet schema version станет **2**.
4. Запустить соответствующий planet EXE на другом порту. Версия 0.15.0 с schema version=1 не считается совместимой и вернёт readiness 503; это не потеря колоний.
5. Обновить страницу. Старые площадки подготавливаются постепенно, только на поверхностях с колониями; запрашивать/генерировать все планеты мира не нужно.

Пример планетарного процесса в отдельном PowerShell:

```powershell
$env:DATABASE_URL = 'postgres://cosmos_planet:URL_ENCODED_PASSWORD@127.0.0.1:5432/existing_database?sslmode=disable'
$env:DB_SCHEMA = 'cosmosimulator'
$env:PLANET_HTTP_ADDR = '127.0.0.1:8081'
.\downloads\cosmosimulator-planet-v0.16.0-windows-amd64.exe
```

Для ограниченной planet DB-роли права P2-1 прежние: SELECT marker/lease и UPDATE lease. Новые таблицы и функция принадлежат космической службе; планетарный процесс их пока не меняет. Привилегии cosmic runtime на новые объекты выдаёт владелец схемы, если используется отдельная DDL-роль. [SCM и конфигурация P2-1](../P2-1/README.ru.md) остаются применимы, но пути EXE должны указывать на текущую сборку.

Административный reset по-прежнему запрещён при зарегистрированных визитах/неполученных возвратах. После разрешённого reset новые зависимости удаляются явно в FK-порядке, dirty trigger не создаёт очередь заново для retiring surface. Астрономическая планета и финансовые гарантии первой очереди сохраняются.

Для отката согласованно остановить обе службы и использовать соответствующий backup/план обратной миграции. Не запускать старый cosmic reset поверх новых FK и не удалять новые таблицы на работающем сервере. Остановка planet сама по себе отката cosmic не требует.
