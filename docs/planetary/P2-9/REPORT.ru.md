# Отчёт P2-9 · 0.23.0

Дата: 31 октября 2026. Выполнен отдельный нагрузочный сценарий с **двумя настоящими исполняемыми процессами и 50 авторизованными WebSocket-клиентами**, общей изолированной PostgreSQL и обычными HTTP/handoff/scene/WS интерфейсами через cosmic gateway. [Исходный JSON](checks/load.json) · [лог сценария](checks/load.txt).

## Результат

Все 13 фаз завершены. Клиенты получили подтверждения 2600 команд движения. В проверяемых сценариях не обнаружены protocol errors, неожиданные разрывы, нарушение server_seq, превышение серверной скорости или дубли presence. При движении, burst и массовых входах не было path_queue_full/path_budget отказов; SQL и WS write_errors на снимках равны нулю.

После 50 переходов записано ровно 50 receipts, повтор confirm не удвоил операцию. После жёсткого завершения planet во время движения замена дождалась нового lease/fence, все 50 пилотов сохранили actor/visit, сектор и точные координаты последнего подтверждённого checkpoint. Cosmic продолжал отвечать на fleet API и выполнять обычные тики. Это восстановление сохранённого состояния, не обещание сохранности движения после последнего checkpoint.

После возврата: 50 сохранённых персонажей, 0 живых визитов, 0 активных акторов/закреплённых кораблей, 0 кэшированных сцен после тестового idle TTL. Остались те же 6 колоний, 5 площадок, 50 кораблей игроков и суммарно 2 049 000 CR игроков. Canonical surface hash не изменился; все сохранённые позиции проходимы.

## Среда и профиль

Linux amd64, Go 1.27.3, PostgreSQL 17.11 (Debian), AMD EPYC 9V74. Тесту видны 5 logical CPU, cgroup quota — 4 CPU и 32 GiB памяти. PostgreSQL и генератор нагрузки находятся в той же облачной среде; это не измерение WAN/целевого Windows-хоста.

На каждый сервер задано 8 соединений БД, scene capacity 32, idle TTL 2s, lease 9s/renew 3s и DB timeout 2s. Cosmic tick настроен на 2s, фоновый worker продолжает деятельность ботов. Настройки по умолчанию игры не изменены. Активная часть измерений длится около 94 секунд, с построением fixture/сборкой весь тест — около 102 секунд.

## Фазы

## Задержки и память

- Подтверждение команды по loopback: p50 **17.5 ms**, p95 **51.6 ms**, p99 **67.7 ms**, накопительный max **78.2 ms**. Всего 2600 подтверждений; квантили относятся к последним 2048.
- На снимке после burst p99 lag планетарной симуляции **1.23 ms**, max **1.63 ms**. Это опоздание обработки scheduled 50ms tick, а не полная end-to-end задержка клиента.
- На том же снимке A* compute p99 **0.072 ms**, очередь p99 **0.34 ms**, dirty checkpoint p99 **56.4 ms**. Окна метрик накоплены к указанной фазе, не являются отдельной выборкой только её последних пяти секунд.
- На последнем снимке cosmic tick duration p99 **48.5 ms**; ошибок тика не зафиксировано. Worker проверяет clock раз в секунду, поэтому заданные 2s не означают жёсткое realtime-расписание: в коротких фазах интервал фактически около 2–3s. Правила начислений/экономики в этом выпуске не менялись.
- Из секундных samples: peak RSS planet **59.5 MiB**, cosmic **43.0 MiB**, peak Go heap alloc planet **36.5 MiB**. Короткие межсэмпловые пики могут быть выше. OS RSS не обязан немедленно уменьшаться после освобождения сцены/GC.

Пул действительно ожидал свободные соединения при массовом входе, но отменённых acquire не было. Накопленное время всех ожиданий параллельных клиентов нельзя читать как latency одного запроса. Во время ходьбы присутствия работают по секторам; намеренные mailbox coalesces сохраняют последнюю полную membership-выборку, итоговый resync не оставляет призраков.

## Изменения кода

Добавлен общий `platform/telemetry`: ограниченное окно задержек, SQL counters без хранения SQL/аргументов, process/pgxpool snapshot. В movement/runtime/planetserver измеряются lag/A*/очередь, coalescing, cold load/eviction, checkpoints и исходящие JSON. В simulation — длительность тика и опоздание цикла. Агрегаты доступны только администратору через два GET endpoints; проверки сессии/роли выполняются заново.

Три `planet_load*230_test.go` файла разделяют сценарий, клиента протокола и управление только собственными процессами. Отдельный workflow `Planetary process load` запускается вручную на своей PostgreSQL service. Нового публичного действия «нагрузить рабочую игру» нет.

Новых таблиц/миграций нет, marker остаётся 7. Ограниченному логину planet для metrics требуется дополнительный `SELECT(role)` на users; чтение кошельков/паролей и cosmic writes по-прежнему запрещены. [Полный GRANT](../P2-10/DATABASE.ru.md).

- [Race восстановления/переходов/ограниченных прав](checks/recovery-race.txt), `go vet ./...` и обе Windows x64 кросс-сборки прошли. [Матрица требований](COVERAGE.ru.md).

До этого этапа не было воспроизводимого двухпроцессного эксперимента на 50 пилотов и показателей для оценки нагрузки. Это устранено harness/метриками/отчётом. В самом новом тесте исправлены три неверных предположения: число всех кораблей не фиксировано, потому что боты создают свой флот; произвольный шаг по X у границы может упираться в препятствие, поэтому выбирается достижимая цель; штатный EOF после visit.ended не считается аварией соединения. Эти исправления относятся к инструменту проверки, не выдаются за найденные ошибки игры.

## Практические ограничения

Профиль подтвердил 50 клиентов при указанных длительностях/условиях, а не предел ёмкости или стабильность на сутки. Пятьдесят браузеров с Canvas не запускались: это протокольная нагрузка, реальные браузерные сценарии проверяются отдельно.

Трафик общего движущегося сектора достигает примерно 4.6 MiB/s JSON: при выборе публичного хостинга важно учитывать исходящий канал. Разделение на пять секторов снижает передачу, потому что клиенты не получают чужие локации. Дополнительные binary/compression/AOI-протоколы этим выпуском не вводились.

Окончательная художественная приёмка preview, нативный Windows SCM/производительность и длительный soak остаются за рамками выполненного измерения. Инструкция эксплуатации и комплект выпуска сведены в [P2-10](../P2-10/README.ru.md).
